1. What is Bash scripting?

Bash stands for Bourne Again Shell. It is a command-line shell commonly available on Ubuntu. A Bash script is a text file containing commands that Bash executes in sequence, with support for variables, conditions, loops, and functions.

Imagine you manually perform these steps every morning:

  1. Check disk space.
  2. Check available memory.
  3. Check whether Nginx is running.
  4. Review recent application errors.
  5. Write down the results.

A Bash script can automate much of this routine.

You run one command

./health_check.sh

Bash executes the script

Reads commands from top to bottom

Checks

Disk, memory, services

Reports

Status and diagnostics

Typical DevOps uses include deployments, backups, log analysis, scheduled health checks, cleanup tasks, and pre-deployment validation.

2. Create and run your first Bash script

Run these commands in your Ubuntu terminal:

mkdir -p ~/devops-lab
cd ~/devops-lab
nano hello.sh

Enter the following content:

#!/usr/bin/env bash

echo "Hello, DevOps learner!"
echo "Current user: $(whoami)"
echo "Current date: $(date)"
echo "Current directory: $(pwd)"

Save in Nano with Ctrl+O, press Enter, and exit with Ctrl+X.

Run it using either method:

bash hello.sh

Or make it executable and run it directly:

chmod +x hello.sh
./hello.sh

Expected output will resemble:

Hello, DevOps learner!
Current user: your_username
Current date: ...
Current directory: /home/your_username/devops-lab

What does each part mean?

  • #!/usr/bin/env bash — the shebang; identifies Bash as the interpreter when the script is executed directly.
  • echo — prints text to standard output.
  • $(whoami) — runs a command and substitutes its output.
  • chmod +x — adds execute permission.
  • ./hello.sh — executes the script in the current directory. The ./ matters because the current directory usually isn't searched through PATH.

A script doesn't need to be executable when you explicitly run it using bash hello.sh.

3. Shell variables

A variable stores a value you can reuse throughout your script.

#!/usr/bin/env bash

APP_NAME="journal-validator"
ENVIRONMENT="staging"
PORT=8080

echo "Application: $APP_NAME"
echo "Environment: $ENVIRONMENT"
echo "Port: $PORT"

Remember these rules:

  • No spaces around = when assigning a value.
  • Use $VARIABLE or ${VARIABLE} to access its value.
  • ${VARIABLE} is often clearer when joining it with other text.

For example:

APP_NAME="journal-validator"

echo "$APP_NAME is starting"
echo "${APP_NAME}_backup"

Output:

journal-validator is starting
journal-validator_backup

Compare the assignment forms:

APP_NAME="my app"  # Correct
# APP_NAME = "my app"  # Incorrect assignment syntax

Environment variables

Environment variables are values made available to programs launched by a process.

echo "$HOME"
echo "$PATH"
echo "$USER"

To set a variable for a single command:

APP_ENV=staging bash -c 'echo "$APP_ENV"'

To export a variable for child processes launched afterward:

export APP_ENV=staging

Note that shell variables aren't automatically exported to child processes. Also, variables set inside a script generally do not change the parent terminal's environment.

4. Quoting: one of the most important Bash skills

Quoting prevents spaces and special characters from unexpectedly changing how commands behave.

Suppose a directory is named journal delivery.

Without quotes:

REPORT_DIR="/tmp/journal delivery"
ls $REPORT_DIR

The shell splits the expanded value into separate words, so ls may interpret it as two paths.

With quotes:

ls "$REPORT_DIR"

Now it is passed as one path.

Three quoting styles

Double quotes: "..."

Expand variables and command substitutions while preserving spaces.

NAME="Ubuntu Server"
echo "Hello, $NAME"

Single quotes: '...'

Treat the contents literally; variables are not expanded.

echo 'Hello, $NAME'

Output: Hello, $NAME

No quotes

The shell may split words and expand wildcard characters such as *.

ls *.log

DevOps rule: Quote variable expansions by default, especially filenames and directory paths:

cp "$SOURCE_FILE" "$DESTINATION_DIR/"

When working with a list of filenames, don't store the list in one ordinary string and expect quoting to preserve each filename as a separate item. Use Bash arrays or safely handle each path individually.

5. Command substitution and exit codes

Command substitution: $(...)

Use command substitution to save the output of a command in a variable.

CURRENT_USER=$(whoami)
CURRENT_DATE=$(date +%F)
DISK_REPORT=$(df -h /)

echo "User: $CURRENT_USER"
echo "Date: $CURRENT_DATE"
echo "$DISK_REPORT"

The command inside $() runs first, and its output becomes the value.

Exit codes: $?

Commands return an exit status. Conventionally:

  • 0 means success.
  • A nonzero value indicates failure or another unsuccessful outcome.

Example:

ls /etc
echo "$?"

ls /directory-that-does-not-exist
echo "$?"

The first command should normally return 0. The second should return a nonzero status.

Important: $? holds the exit status of the most recently executed command. If you run echo first, you'll see the status of echo, not the earlier command.

A better pattern is:

if ls /etc >/dev/null 2>&1; then
    echo "Directory check succeeded"
else
    echo "Directory check failed"
fi

Here, >/dev/null discards normal output and 2>&1 redirects error output to the same destination. The condition checks the command's status directly.

You can also use && and ||:

mkdir -p "$HOME/devops-lab/reports" && echo "Directory ready"

&& runs the next command only if the preceding command succeeds. || runs the next command if it fails. For scripts involving several steps, explicit if blocks are often easier to read and debug.

6. Conditions: if, elif, and else

Conditions allow a script to make decisions.

#!/usr/bin/env bash

DISK_USAGE=72

if (( DISK_USAGE >= 90 )); then
    echo "CRITICAL: Disk usage is high"
elif (( DISK_USAGE >= 75 )); then
    echo "WARNING: Disk usage is elevated"
else
    echo "OK: Disk usage is within the configured threshold"
fi

With DISK_USAGE=72, the script prints:

OK: Disk usage is within the configured threshold

The (( ... )) syntax is useful for integer arithmetic and numeric comparisons in Bash.

Test files, directories, and strings

Use [[ ... ]] for many common Bash tests:

LOG_FILE="/var/log/syslog"

if [[ -f "$LOG_FILE" ]]; then
    echo "Log file exists"
else
    echo "Log file is missing or is not a regular file"
fi

Common tests:

Test Meaning
-f "$FILE" Regular file exists
-d "$DIR" Directory exists
-r "$FILE" File is readable
-x "$FILE" File is executable, or a directory is searchable
-z "$VALUE" String is empty
"$A" == "$B" Strings are equal inside [[ ... ]]

For numeric comparisons, you can use arithmetic syntax:

if (( COUNT > 5 )); then
    echo "More than five items"
fi

For command success, prefer testing the command itself:

if systemctl is-active --quiet cron; then
    echo "Cron is active"
else
    echo "Cron is not active"
fi

This is more reliable than comparing the printed output of a command when you only need to know whether it succeeded.

7. Loops: automate repeated tasks

A. for loop

Use a for loop when you know which items you want to process.

#!/usr/bin/env bash

for SERVICE in cron ssh; do
    if systemctl is-active --quiet "$SERVICE"; then
        echo "$SERVICE: active"
    else
        echo "$SERVICE: not active"
    fi
done

This checks two services without duplicating the same logic.

Service names can vary by Ubuntu installation. For example, the OpenSSH service is commonly named ssh on Ubuntu, while other distributions may use a different name.

B. Loop through files

Create some practice files:

mkdir -p ~/devops-lab/logs
touch ~/devops-lab/logs/app.log
touch ~/devops-lab/logs/worker.log

Now list the matching log files:

for FILE in "$HOME"/devops-lab/logs/*.log; do
    if [[ -f "$FILE" ]]; then
        echo "Found log: $FILE"
    fi
done

The [[ -f "$FILE" ]] check helps avoid treating an unmatched wildcard as a real filename.

C. while loop

A while loop repeats while its condition succeeds.

#!/usr/bin/env bash

COUNT=1

while (( COUNT <= 5 )); do
    echo "Attempt $COUNT"
    ((COUNT += 1))
done

Output:

Attempt 1
Attempt 2
Attempt 3
Attempt 4
Attempt 5

In real automation, loops are useful for retrying a health check, checking a list of servers, or processing files. Always design a clear stopping condition for retry loops so a failed operation doesn't run forever.

8. Functions: write reusable code

A function gives a name to a block of commands.

#!/usr/bin/env bash

greet() {
    local NAME="$1"
    echo "Hello, $NAME"
}

greet "DevOps learner"
greet "Ubuntu administrator"

Output:

Hello, DevOps learner
Hello, Ubuntu administrator

Key concepts:

  • greet() defines a function.
  • $1 inside the function refers to its first argument.
  • local makes the variable local to the function.
  • greet "DevOps learner" calls the function.

Functions can also return status codes:

check_directory() {
    local DIR="$1"

    if [[ -d "$DIR" ]]; then
        echo "Directory exists: $DIR"
        return 0
    else
        echo "Directory missing: $DIR"
        return 1
    fi
}

if check_directory "$HOME/devops-lab"; then
    echo "Continuing with the task"
else
    echo "Please check the directory"
fi

In Bash, return is used to return a status code from a function, not to return arbitrary text. Use standard output when a function needs to produce text.

9. Positional arguments: pass values to your script

Arguments make a script reusable without editing its source code every time.

Create a file called app_info.sh:

#!/usr/bin/env bash

APP_NAME="${1:-myapp}"
ENVIRONMENT="${2:-development}"

echo "Application: $APP_NAME"
echo "Environment: $ENVIRONMENT"
echo "Script name: $0"
echo "Number of arguments: $#"

Run:

bash app_info.sh journal-validator staging

Example output:

Application: journal-validator
Environment: staging
Script name: app_info.sh
Number of arguments: 2
Expression Meaning
$0 Script name or invocation path
$1, $2 First and second positional arguments
$# Number of arguments
"$@" All arguments, preserved as separate items when quoted
${1:-myapp} First argument, or a default if unset or empty

Why does "$@" matter? Consider a script that passes all arguments to another command:

printf 'Argument: %s\n' "$@"

Run:

bash app_info.sh "journal validator" staging

The quoted application name is one argument, even though it contains a space.

Best practice: Validate required arguments before using them in operations such as deployment, backup, or cleanup.

10. Safe scripting practices

Automation is powerful because it can perform the same action many times. A mistake can also repeat many times, so safety belongs in the script itself.

Quote variable expansions

Prefer "$FILE" over $FILE when using filenames and paths.

Check inputs and prerequisites

Verify arguments, directories, commands, permissions, and configuration before changing anything.

Avoid destructive defaults

Don't casually automate rm -rf, recursive permission changes, or disk operations. Inspect targets and use explicit safeguards.

Log and report failures

Include timestamps, meaningful messages, and appropriate exit codes so failures can be diagnosed.

Should you use set -Eeuo pipefail?

You will often see this near the top of scripts:

set -Eeuo pipefail

Here's what the options generally mean:

  • -e: exit on many unhandled command failures.
  • -u: treat expansion of unset variables as an error.
  • -o pipefail: make a pipeline fail if a command in it fails, rather than only considering the last command's status.
  • -E: allow ERR traps to be inherited in more contexts.

These options are helpful, but they do not make a script automatically safe or correct. -e has exceptions, particularly around conditions, pipelines, and compound commands. Explicitly handle expected failures with if, and test your scripts using realistic inputs.

For example:

#!/usr/bin/env bash
set -Eeuo pipefail

if ! command -v df >/dev/null 2>&1; then
    echo "ERROR: df command not found" >&2
    exit 1
fi

echo "Required command is available"

The >&2 sends the error message to standard error. The exit 1 indicates failure to the calling shell or scheduler.

Additional safeguards

  • Use absolute paths in production scripts when practical.
  • Avoid embedding passwords, tokens, or private keys in scripts.
  • Don't run everything with sudo; use the least privilege required.
  • Test on sample data before production data.
  • Make repeated runs safe where possible (idempotency).
  • Set timeouts for operations that might hang.
  • Don't assume that a successful command means the overall task succeeded.
  • Use Git or another version-control system to track script changes.

11. Realistic DevOps case study: automate a server health check

The scenario

Your Ubuntu server hosts a journal validation application. A support engineer manually checks disk usage and whether the application service is running. You want one script that reports the server's basic health without changing the system.

The workflow:

1. Start the health-check script

2. Check prerequisites and disk usage

3. Check the requested service

4. Print findings and return a status

Step A — Create the script

cd ~/devops-lab
nano health_check.sh

Paste the following complete script:


#!/usr/bin/env bash
set -Eeuo pipefail

# Usage: ./health_check.sh [service_name] [disk_warning_percent]

SERVICE="${1:-cron}"
DISK_WARNING="${2:-80}"

# Validate the threshold before using it.
if [[ ! "$DISK_WARNING" =~ ^[0-9]+$ ]] ||
   (( DISK_WARNING < 1 || DISK_WARNING > 100 )); then
    echo "ERROR: Disk threshold must be an integer from 1 to 100." >&2
    exit 2
fi

# Ensure required commands exist.
for CMD in df awk systemctl date; do
    if ! command -v "$CMD" >/dev/null 2>&1; then
        echo "ERROR: Required command not found: $CMD" >&2
        exit 1
    fi
done

log() {
    printf '[%s] %s\n' "$(date '+%F %T')" "$*"
}

check_disk() {
    local usage

    usage=$(df -P / | awk 'NR == 2 {
        gsub(/%/, "", $5)
        print $5
    }')

    if [[ ! "$usage" =~ ^[0-9]+$ ]]; then
        log "ERROR: Could not read root filesystem usage."
        return 1
    fi

    log "Root filesystem usage: ${usage}%"

    if (( usage >= DISK_WARNING )); then
        log "WARNING: Disk usage reached the configured threshold (${DISK_WARNING}%)."
        return 1
    fi

    log "Disk check: OK"
    return 0
}

check_service() {
    local service="$1"

    if systemctl is-active --quiet "$service"; then
        log "Service '$service': active"
        return 0
    else
        log "WARNING: Service '$service' is not active."
        return 1
    fi
}

main() {
    local failed=0

    log "Starting server health check"
    log "Service requested: $SERVICE"

    check_disk || failed=1
    check_service "$SERVICE" || failed=1

    if (( failed == 0 )); then
        log "Health check completed: PASS"
        return 0
    else
        log "Health check completed: ATTENTION REQUIRED"
        return 1
    fi
}

main "$@"

Save the file, then make it executable:

chmod +x health_check.sh

Step B — Run it

Check the cron service with an 80% disk warning threshold:

./health_check.sh cron 80

You might see output similar to:

[2026-10-25 10:00:00] Starting server health check
[2026-10-25 10:00:00] Service requested: cron
[2026-10-25 10:00:00] Root filesystem usage: 42%
[2026-10-25 10:00:00] Disk check: OK
[2026-10-25 10:00:00] Service 'cron': active
[2026-10-25 10:00:00] Health check completed: PASS

Your timestamps and disk usage will differ.

To test a different service:

./health_check.sh ssh 90

To test input validation:

./health_check.sh cron 150

The last command should exit with status 2, because 150 is outside the permitted range.

Step C — Understand the important design decisions

  • Reusable: Service name and threshold are arguments.
  • Safe by default: It only reads status information; it does not restart services or delete files.
  • Validated: The threshold is checked before use.
  • Observable: Each major check prints a timestamped message.
  • Failure-aware: A failed check makes the script report attention required and return a nonzero status.
  • Explicit: The script checks both disk usage and service status instead of assuming one check proves the entire server is healthy.

This is a basic example, not a full production monitoring system. systemctl is-active checks service state, not whether the application can actually serve requests. A production health check may also need HTTP requests, dependency checks, alerting, timeouts, and log retention.

Step D — Inspect the exit status

Immediately after running the script:

./health_check.sh cron 80
STATUS=$?
echo "Script exit status: $STATUS"

Expected interpretation:

Status Meaning
0 All implemented checks passed
1 A check or prerequisite failed
2 Invalid threshold argument

The status codes above describe this particular script, not universal Bash rules.

15. Bash scripting cheat sheet

Keep this reference handy when writing your next automation script.

A reusable starting template

Copy this template when beginning a new script:


#!/usr/bin/env bash
set -Eeuo pipefail

usage() {
    echo "Usage: $0 <name>" >&2
}

main() {
    if (( $# != 1 )); then
        usage
        return 2
    fi

    local name="$1"
    printf 'Hello, %s!\n' "$name"
}

main "$@"

Test it before adding more functionality:

bash -n script.sh
bash script.sh Ubuntu
bash script.sh

The first command checks syntax without running the script. The second provides the required argument. The third deliberately tests the missing-argument path.
