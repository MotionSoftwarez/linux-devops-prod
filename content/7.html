Linux for DevOps — Module 1, Lesson 6

Linux users, groups, and sudo

Beginner

Practical lab

Server security

In DevOps, several people and services may use the same Linux server. A deployment engineer might need to update application files, while a monitoring service only needs to read logs.

Linux uses users, groups, file permissions, and controlled administrative privileges to manage this access safely.

By the end of this lesson, you'll understand how to identify your user, inspect group membership, look up accounts, create and modify users, change passwords, and run authorized commands with sudo.

1. Visualize Linux users and groups

Imagine a server running a website. Different accounts have different responsibilities.

Linux server

Hosts application files, logs, and services

Users

deploy, alice, bob, www-data

Individual accounts that run commands or services

Groups

webteam, developers, monitoring

Collections of users that can share access

Access controls

File permissions, group membership, and sudo policy

For example:

  • alice belongs to the developers group.
  • bob belongs to the monitoring group.
  • Both may be allowed to log in, but neither automatically receives administrator privileges.
  • A service account such as www-data may run a web server without being used for ordinary interactive logins.

A user is an account. A group is a way to organize users for shared access. A privileged command is an operation that requires permissions beyond those of the current user.

2. Identify yourself with whoami

Run:

whoami

Example output:

pawan

This reports the effective username associated with the current command context. It's useful when you've switched users or entered a shell on a remote server.

Try these related commands:

id
groups

Example output from id:

uid=1001(pawan) gid=1001(pawan) groups=1001(pawan),1005(webteam)

How to read it:

Term Meaning
uid Numeric user ID
gid Numeric ID of the primary group
groups Groups associated with the current process credentials
pawan Example account name
webteam Example supplementary group

The names and numbers above are illustrative; your actual output will differ.

whoami vs id vs groups

Command What it tells you
whoami Effective username
id User ID, primary group, and group memberships
groups Group names associated with the user or specified account

Try:

groups
groups deploy
id deploy

The last two commands inspect the account named deploy, if it exists and your system can resolve it.

3. Look up accounts with getent

Linux account information can come from local files or a centralized identity service, such as LDAP. getent queries the system's configured account databases.

Look up a user:

getent passwd deploy

Example output:

deploy:x:1002:1002:Deployment User:/home/deploy:/bin/bash

The fields are separated by colons:

Understand the account record

deploy : x : 1002 : 1002 : Deployment User : /home/deploy : /bin/bash

1. Username

Account name

2. Password placeholder

x usually means password data is stored separately, commonly in /etc/shadow

3. UID

Numeric user ID

4. Primary GID

Numeric primary group ID

5. GECOS

Optional descriptive account information

6. Home directory

The user's home path

7. Login shell

The shell configured for the account

Look up a group:

getent group webteam

Example output:

webteam:x:1050:deploy,alice

This indicates that webteam has GID 1050 and lists deploy and alice as supplementary members in this example. A user's primary group is not necessarily listed in that final member field.

Useful lookups

getent passwd
getent group
getent group sudo

The first two may return many records. On Ubuntu, the sudo group commonly identifies users authorized for administrative access through the default sudo policy, but actual permissions depend on the configured policy.

4. Create a user with useradd

Creating users generally requires administrator privileges.

First, understand the command:

sudo useradd -m -s /bin/bash deploy
  • sudo — request execution with elevated privileges.
  • useradd — create a user account.
  • -m — create a home directory if needed.
  • -s /bin/bash — set Bash as the login shell.
  • deploy — the new account name.

Then set a password interactively:

sudo passwd deploy

The system will prompt you to enter and confirm the new password. Password input may not appear on the screen while you type; that is normal.

Verify the account:

getent passwd deploy
id deploy
ls -ld /home/deploy

Important: A created account does not automatically have administrative privileges. Account creation, password setup, SSH access, group membership, and service permissions are separate concerns.

5. Modify users with usermod

usermod changes attributes of an existing user account.

Add a user to a supplementary group

sudo usermod -aG webteam deploy

Meaning:

  • -a — append to existing supplementary groups.
  • -G webteam — specify the supplementary group.
  • deploy — account to modify.

Critical rule: Use -aG when adding supplementary group membership. Using -G without -a can replace the user's existing supplementary group list.

Verify the configured group membership:

id deploy
getent group webteam

A running process or an existing login session may not immediately reflect changed group memberships. A new login session is often needed.

Other useful examples

Change the user's login shell:

sudo usermod -s /bin/bash deploy

Lock an account's password authentication:

sudo passwd -l deploy

Unlock it:

sudo passwd -u deploy

Password locking is not a universal guarantee that every login method is disabled; SSH keys and other authentication mechanisms may behave differently. For a departing employee or compromised account, follow the organization's full account-disablement procedure.

6. Understand passwd

The passwd command manages account passwords.

Change your own password:

passwd

Change another user's password as an authorized administrator:

sudo passwd deploy

Additional account administration commands:

sudo passwd -S deploy
sudo passwd -l deploy
sudo passwd -u deploy

passwd -S reports password status information on common Linux distributions.

Security habits

  • Never place a real password directly in a shell command or script.
  • Don't share /etc/shadow contents; it contains sensitive password authentication data.
  • Use a unique, strong password when password authentication is required.
  • Follow your organization's identity and account lifecycle procedures.
  • Prefer managed SSH keys or an approved identity system where appropriate.

7. Use sudo safely

sudo allows an authorized user to run a command with elevated privileges, according to the system's sudo policy.

For example, viewing a protected log might require:

sudo less /var/log/auth.log

On systems using systemd, service logs can often be queried with:

sudo journalctl -u nginx --since "1 hour ago"

Check whether you have sudo access:

sudo -l

This displays the commands your account is allowed to run through sudo, subject to the policy and any required authentication.

Why sudo matters

Compare these commands:

cat /etc/hostname
sudo systemctl status nginx

The first typically works for an ordinary user. The second may require elevated privileges depending on the system's policy.

sudo doesn't make every command safe. A destructive command executed with elevated privileges can affect the entire server.

Visualize privilege escalation

Ordinary user

Has limited permissions

sudo command

System checks the sudo policy and may request authentication

Authorized

Not authorized

Command is denied by policy

sudo versus su

Command Purpose
sudo command Run a specific command with authorized elevated privileges
sudo -i Start an interactive login shell as root, if authorized
su - username Switch to another user's login environment, usually requiring that account's password or other configured authorization
whoami Check the effective username of the current shell

For day-to-day DevOps work, prefer running the specific command that needs elevated privileges rather than staying in a root shell.

Never use sudo to bypass a permission problem without understanding the cause. The correct fix might be a group membership, ownership adjustment, or deployment configuration—not permanent root execution.

8. Realistic DevOps case study: onboarding a deployment engineer

Scenario: A new team member needs to deploy an application and read its logs. The team wants to avoid granting full administrator access unnecessarily.

Assume the following accounts and groups are appropriate for your organization's policy:

  • New engineer: alice
  • Deployment account: deploy
  • Shared application group: webteam

The following commands are examples for an administrator in a disposable lab or an approved server change. Do not run account-management commands on a production server without authorization.

Step 1 — Check whether the account exists

getent passwd alice
getent group webteam

If the account lookup returns no record, confirm that the account truly needs to be created and that it isn't managed by a central identity provider.

Step 2 — Create the user, if approved

sudo useradd -m -s /bin/bash alice
sudo passwd alice

Step 3 — Add the user to the shared group

sudo usermod -aG webteam alice

Verify:

id alice
getent group webteam

Step 4 — Check the application's ownership and permissions

ls -ld /srv/myapp
ls -l /srv/myapp

Do not assume the whole application directory should be writable by the deployment team. Application code, secrets, runtime data, and logs often need different access policies.

Step 5 — Grant only the required access

If the directory is deliberately configured for webteam access, use the approved group and permission model. For example, an administrator might use group ownership and group read/execute permissions on a specific shared directory.

sudo chgrp webteam /srv/myapp
sudo chmod 750 /srv/myapp

This changes the group and mode of the directory itself—not its contents. Before applying it, verify that the directory's intended owner, group, and service access are compatible with the change.

Step 6 — Check administrative privileges separately

sudo -l -U alice

Where supported, this checks the sudo policy for alice. Group membership alone should not be treated as proof of what commands the user can run.

Expected result: Alice can access only the resources allowed by the final permissions and system policy. Being in webteam does not automatically grant full root access.

Case study lesson

A good DevOps engineer doesn't solve every access issue by adding users to the sudo group. They grant the minimum permissions required for the job, verify the outcome, and document the change.

12. Cheat sheet

Users, groups, and sudo

Copy commands

Command Purpose
whoami Show effective username
id Show UID, GID, and groups
groups Display group membership
getent passwd USER Look up a user account
getent group GROUP Look up a group
sudo useradd -m USER Create a user with a home directory
sudo passwd USER Set or change a user's password
sudo usermod -aG GROUP USER Add a user to a supplementary group
sudo passwd -S USER Inspect password status
sudo passwd -l USER Lock password authentication
sudo -l Inspect current sudo privileges
sudo -l -U USER Inspect another user's sudo policy, where permitted

Replace USER and GROUP with the intended account and group names. Commands that modify accounts normally require appropriate privileges.

Five principles to remember

  1. Identify first: use whoami and id.
  2. Look up before changing: use getent to verify existing accounts and groups.
  3. Preserve group memberships: use usermod -aG when adding a supplementary group.
  4. Protect credentials: use interactive password tools and avoid exposing secrets.
  5. Follow least privilege: grant only the access necessary for the task.
