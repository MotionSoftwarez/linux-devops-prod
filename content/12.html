1. What are Linux logs?

A log is a record of something that happened on a system or application. Linux services write logs to help administrators understand normal activity, warnings, errors, and failures.

Imagine that your Python web application stops responding. Instead of immediately restarting the server, you inspect its logs to find out what happened.

Common log examples:

  • Started nginx.service — a service started.
  • Permission denied — a process couldn't access a file or directory.
  • Connection refused — a connection attempt was rejected, often because no service was listening on that port.
  • No space left on device — a filesystem or another storage resource is full.
  • Traceback — a Python program encountered an exception.

There are two important places to investigate:

  1. systemd journal: centralized records from services and the system, queried using journalctl.
  2. /var/log: a directory containing many traditional log files, including application and service logs.

Some services write to both; others mainly use one or the other.

2. Explore /var/log

Start with these read-only commands.

# List log directories and files
ls -lah /var/log

# Show the largest entries in a readable format
du -sh /var/log/* 2>/dev/null

# Identify the Ubuntu version
cat /etc/os-release

The second command estimates the size of each top-level entry. It may omit hidden entries and some inaccessible content.

Common log files and directories

Path Typical purpose
/var/log/syslog General system messages on many Ubuntu installations
/var/log/auth.log Authentication and authorization events on systems using this log
/var/log/kern.log Kernel messages, where configured
/var/log/dpkg.log Package installation and removal activity
/var/log/apt/ APT package-manager logs
/var/log/nginx/access.log Nginx HTTP requests, if configured
/var/log/nginx/error.log Nginx errors, if configured
/var/log/journal/ Persistent systemd journal storage, if enabled

Important: Not every file exists on every Ubuntu server. Some systems use the systemd journal without maintaining traditional syslog or auth.log files. Application log paths also depend on their configuration.

Try exploring safely:

ls -lah /var/log
ls -lah /var/log/nginx/

If Nginx isn't installed, the second command may report that the directory doesn't exist. That is not, by itself, a system problem.

3. Read logs using less, tail, and grep

These three tools are essential for everyday Linux troubleshooting.

less — read a log comfortably

less /var/log/syslog

Navigate with the arrow keys or Page Up/Page Down. Press /error to search for error, n for the next match, and q to quit. Search terms are case-sensitive by default.

tail — inspect the latest entries

tail -n 50 /var/log/syslog

Show the last 50 lines. To watch new lines arrive:

tail -f /var/log/syslog

Stop following with Ctrl+C. For a log that may be replaced during rotation, try tail -F /var/log/syslog.

grep — find matching text

grep -i "error" /var/log/syslog

Find lines containing error, regardless of capitalization. Add line numbers using -n:

grep -in "failed" /var/log/syslog

If a log is large, filter it instead of printing the entire file.

Useful command patterns

| Goal | Command |
|---|---|
| Show the last 100 lines | tail -n 100 app.log |
| Search without case sensitivity | grep -i "timeout" app.log |
| Show matching line numbers | grep -n "ERROR" app.log |
| Count matching lines | grep -c "ERROR" app.log |
| Search for several patterns | grep -Ei "error|failed|timeout" app.log |
| Search files under a directory | grep -Rni "permission denied" /var/log/myapp/ |
| Read a long file with search | less app.log |

Replace app.log with the real path on your server.

Combine commands with pipes

A pipe (|) sends the output of one command to another command.

grep -i "error" /var/log/syslog | tail -n 20

This finds matching lines and displays the last 20 matches.

For a Python application's log:

grep -inE "traceback|exception|error|failed" /opt/myapp/logs/app.log

This searches for several common failure indicators. Remember that not every occurrence of “error” represents an outage, and some failures use different wording.

Permission note: If a log is unreadable, first check its permissions and ownership. Use sudo only when necessary, for example:

sudo less /var/log/auth.log

Avoid running every command as root by habit.

4. Use journalctl to investigate systemd services

The journalctl command reads the systemd journal. It is especially useful when a service fails to start or stops unexpectedly.

Start with these commands

# Show recent journal entries
sudo journalctl -n 50

# Show logs from a specific service
sudo journalctl -u nginx

# Show the latest 50 lines from Nginx
sudo journalctl -u nginx -n 50

# Show entries from the last 30 minutes
sudo journalctl --since "30 minutes ago"

# Follow new journal entries
sudo journalctl -f

For a service-specific live view:

sudo journalctl -u nginx -f

Press Ctrl+C to stop following logs.

Filter by time, boot, and severity

# Logs since midnight today
sudo journalctl --since today

# Logs from the current boot
sudo journalctl -b

# Errors and more severe messages since today
sudo journalctl -p err --since today

# Logs from a specific time window
sudo journalctl --since "2026-10-25 09:00:00" \
  --until "2026-10-25 10:00:00"

The last command uses an example date and time; substitute the relevant time window for your incident.

What do priority levels mean?

Priority Meaning
0 Emergency
1 Alert
2 Critical
3 Error
4 Warning
5 Notice
6 Informational
7 Debug

For example, -p err shows priorities 0 through 3. It does not mean every operational problem will appear as an error-level journal entry.

Visual troubleshooting flow

Service is failing

systemctl status myapp

journalctl -u myapp -n 100

Configuration / file

Check paths, permissions, syntax

Port / dependency

Check listeners and dependencies

Fix the identified cause and verify

The key habit: check the evidence before restarting the service. Restarting too early can remove useful context or temporarily hide the symptom.

5. Realistic DevOps case study: Python application returns HTTP 500

Imagine an Ubuntu server running a Python web application through systemd. Users report that the website returns HTTP 500 after a deployment.

An HTTP 500 response means the server encountered an internal error while handling the request. It does not tell us the exact cause.

Step 1 — Check the service state

sudo systemctl status myapp --no-pager -l

Suppose the service is active (running). That tells us the process is running, but it does not prove every request succeeds.

Step 2 — Inspect recent application logs

sudo journalctl -u myapp -n 100 --no-pager

Imagine the logs contain:

Oct 25 09:14:21 app-server myapp[2418]: Request received: /reports
Oct 25 09:14:21 app-server myapp[2418]: Traceback (most recent call last):
Oct 25 09:14:21 app-server myapp[2418]:   File "/opt/myapp/app.py", line 84, in reports
Oct 25 09:14:21 app-server myapp[2418]: KeyError: 'DATABASE_URL'

This is an illustrative log, not a report from a real server.

The useful clue is KeyError: 'DATABASE_URL': the code tried to access a configuration key that wasn't available in the expected form.

Step 3 — Narrow the search

sudo journalctl -u myapp --since "1 hour ago" --no-pager \
  | grep -inE "traceback|exception|error|failed|DATABASE_URL"

This narrows the output to likely failure messages. If the logs use a different service name or timestamps, adjust the query.

Step 4 — Investigate the configuration safely

Inspect the application's systemd unit:

sudo systemctl cat myapp

Check the Environment= or EnvironmentFile= entries, if present. A unit may reference a separate configuration file, and the application may also obtain configuration from another source.

Check the configured file's existence and permissions without printing secrets:

sudo ls -l /etc/myapp/

If a configuration file is involved, inspect its structure carefully. Do not paste database passwords, API tokens, or other secrets into logs, screenshots, or chat.

Step 5 — Correct the actual cause

If the investigation confirms that the required variable is missing, restore it using the application's approved configuration method. Avoid guessing the correct database URL or exposing credentials.

If a systemd unit or its drop-in configuration was changed, reload unit definitions and restart only when appropriate:

sudo systemctl daemon-reload
sudo systemctl restart myapp
sudo systemctl status myapp --no-pager -l

If only an application environment file was corrected, daemon-reload may not be needed; whether a restart is required depends on how the application loads that file.

Step 6 — Verify the result

sudo journalctl -u myapp --since "5 minutes ago" --no-pager
curl -sS -o /dev/null -w '%{http_code}\n' \
  --connect-timeout 5 http://127.0.0.1:8080/

Replace the port and URL with the application's actual local endpoint. A response code alone is not enough: also test the affected route and review the logs for new errors.

Lesson from the incident: the service was running, but application requests were failing because of a configuration problem. Logs helped identify the failure rather than treating every HTTP 500 as a network issue.

6. Log rotation: prevent logs from filling the disk

Applications can write logs continuously. Without a retention policy, log files can consume significant disk space.

Log rotation is the process of rotating older log files, retaining a chosen history, and sometimes compressing or deleting old files according to a policy.

For example:

Today
app.log

New log entries

Rotation occurs

The current log is renamed or otherwise rotated; a new log may be created

app.log

Current

app.log.1

Previous

app.log.2.gz

Older, compressed

Illustrative naming pattern; actual filenames and retention rules depend on configuration.

Explore Ubuntu's log-rotation configuration

# Check whether logrotate is installed
command -v logrotate

# Read the main configuration
less /etc/logrotate.conf

# List configuration snippets
ls -lah /etc/logrotate.d/

Common settings include:

Setting Purpose
daily Rotate daily
weekly Rotate weekly
rotate 7 Retain seven rotated copies
compress Compress rotated logs
missingok Don't report an error if the log is missing
notifempty Skip rotation for empty files
create Create a replacement log with specified permissions and ownership

These are configuration directives, not commands to run individually in the shell.

Test a rotation configuration safely

# Check the configuration without performing rotation
sudo logrotate -d /etc/logrotate.conf

Debug mode is intended to show what logrotate would do without changing log files. Review its output and confirm the configuration paths before using other modes.

Avoid casually running sudo logrotate -f ... on a production server. Force mode can rotate logs immediately, potentially disrupting an application's logging behavior or complicating an active incident.

Why rotation matters for DevOps

  • Controls disk consumption.
  • Preserves a useful history of incidents.
  • Reduces the size of individual files.
  • Helps prevent applications from exhausting storage.
  • Makes it easier to find older errors—provided retention hasn't deleted them.

One subtle point: a running process may keep writing to an old file descriptor after a log is renamed. Some applications need a reload or a documented signal to reopen their logs. Follow the application's supported procedure rather than deleting logs manually.

7. Check disk space before logs become an incident

A log problem can itself become a system outage.

# Filesystem capacity
df -h

# Inode availability
df -i

# Largest top-level log entries
sudo du -xhd1 /var/log 2>/dev/null | sort -h
  • df -h shows filesystem space in readable units.
  • df -i checks inode availability, which can run out even when some disk space remains.
  • du estimates disk usage. The example stays on the same filesystem with -x and summarizes one directory level.

If the disk is full, first identify what is consuming space. Don't blindly delete logs or remove system files; logs may be essential evidence, and deletion may not free space while a process still holds the file open.

9. Safe log-analysis practices

Start with a narrow time window

Use --since, --until, -u, and -n to reduce noise and focus on the incident.

Protect secrets and personal data

Logs can contain authorization headers, session IDs, email addresses, IP addresses, or tokens. Redact sensitive data before sharing.

Use read-only commands first

Prefer journalctl, less, grep, tail, df, and du before making configuration changes.

Correlate timestamps

Compare application logs with service logs and deployment times. Check timezone and timestamp formats before drawing conclusions.

Don't destroy evidence

Don't truncate logs, remove journal directories, disable logging, or delete log files to "fix" an error. Diagnose the issue and follow retention policies.
