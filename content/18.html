1. What is an environment variable?

An environment variable is a named value that a program can read while it runs. It provides configuration without requiring you to change the program's source code.

For example, your journal validation application might need to know which environment it's running in:

APP_ENV=staging

It could also use settings such as:

APP_NAME=journal-validator
LOG_LEVEL=INFO
PORT=8080

These are examples of ordinary configuration values, not secrets.

Environment variables can control behavior, but they do not automatically create files, start services, or grant permissions. Your application must know how to read and use them.

2. Shell variables versus exported variables

This is one of the most important Linux concepts in this lesson.

A. Create a shell variable

Run:

APP_ENV=staging
echo "$APP_ENV"

Expected output:

staging

The variable exists in your current Bash shell. By default, a shell variable is not automatically passed to child processes.

B. Export the variable

export APP_ENV=staging
bash -c 'echo "$APP_ENV"'

Expected output:

staging

The export command marks the variable for inheritance by child processes.

Compare the two behaviors:

Command Current shell can read it? Child process inherits it?
APP_ENV=staging Yes No, by default
export APP_ENV=staging Yes Yes

Try this example:

APP_ENV=staging
bash -c 'echo "${APP_ENV:-not set}"'

Expected output:

not set

Now run:

export APP_ENV=staging
bash -c 'echo "$APP_ENV"'

Expected output:

staging

The ${APP_ENV:-not set} syntax means: use APP_ENV if it is set and non-empty; otherwise use not set.

C. Run a command with a temporary variable

You can provide a variable for one command without exporting it permanently in your current shell:

APP_ENV=staging bash -c 'echo "$APP_ENV"'

This is useful for testing an application under a different configuration:

APP_ENV=test python3 app.py

This assignment applies to that command and its child processes. It does not permanently change your shell's APP_ENV.

D. Inspect and remove variables

printenv APP_ENV
env
export -p
unset APP_ENV
  • printenv APP_ENV prints the exported value if present.
  • env lists the current process environment.
  • export -p displays exported variables and their values or declarations.
  • unset APP_ENV removes the variable from the current shell.

Security warning: Don't casually paste the output of env or export -p into tickets or chat. It may contain passwords, tokens, or other sensitive configuration.

3. Understanding PATH

PATH tells the shell which directories to search when you enter a command without its full path.

Inspect it:

echo "$PATH"

A typical value might look like:

/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin

Each directory is separated by a colon (:).

How command lookup works

You type python3

The shell searches directories in PATH

It finds an executable—or reports command not found

Check where commands are found:

command -v bash
command -v python3
command -v flock

Example output could be /usr/bin/python3, but your actual paths may differ.

Why PATH matters in cron

Your interactive terminal might know where python3 or a custom tool is installed. Cron typically starts jobs with a smaller environment.

A script that works in your terminal may fail under cron with:

python3: command not found

Use the actual executable path returned by:

command -v python3

For a Python virtual environment, prefer its explicit interpreter, for example:

/opt/myapp/venv/bin/python /opt/myapp/app.py

You can also define a deliberate PATH in a crontab, but do not overwrite it blindly if the script depends on other directories.

4. Where environment variables are configured

Different configuration locations serve different purposes.

Location Typical purpose
Current shell Temporary interactive work
~/.bashrc Bash interactive-shell settings
~/.profile Login-shell environment setup
/etc/environment System-wide environment assignments handled by PAM on common Ubuntu configurations
Crontab Environment for scheduled jobs
systemd unit Environment for a managed service
Application config file Application-specific settings
.env file Convention used by many frameworks and applications

Important: these locations are not interchangeable. For example, cron does not normally read your interactive ~/.bashrc, and a .env file is not automatically loaded by every program.

A. Set a variable for interactive Bash sessions

For a non-secret convenience setting, you might add this to ~/.bashrc:

export EDITOR=nano

Reload the file in the current shell:

source ~/.bashrc

This is useful for interactive-shell preferences. It is generally not the best place to configure a production service or store credentials.

B. Use a configuration file for application settings

For example, an application might use:

APP_ENV=staging
LOG_LEVEL=INFO
PORT=8080

These lines are a configuration format only if your application or a loader understands that format. Bash does not automatically load arbitrary files, and Python does not automatically load .env files unless code or a library does so.

We'll use a controlled pattern in the next section.

5. .env files and safe configuration patterns

A .env file is a common way to store application settings as KEY=value pairs.

For example, create a lab directory:

mkdir -p "$HOME/devops-lab/config"
chmod 700 "$HOME/devops-lab/config"
nano "$HOME/devops-lab/config/app.env"

Add non-secret practice settings:

APP_ENV=staging
APP_NAME=journal-validator
LOG_LEVEL=INFO

Save the file. Protect it from other local users:

chmod 600 "$HOME/devops-lab/config/app.env"
ls -l "$HOME/devops-lab/config/app.env"

The expected permission mode is similar to:

-rw------- ... app.env

This means the file owner can read and write it; group and other users have no access. The parent directory's permissions also matter.

A. Read a configuration file in Bash

For a file containing simple KEY=value assignments, Bash can load it with source:

source "$HOME/devops-lab/config/app.env"
printf 'Environment: %s\n' "$APP_ENV"

However, source executes the file as shell code. Do this only with a file you trust and control. A malicious or modified file could run commands.

Also, sourcing a file does not automatically export every variable. If a child process needs those values, you can export specific variables:

source "$HOME/devops-lab/config/app.env"

export APP_ENV APP_NAME LOG_LEVEL

Alternatively, set -a makes subsequently defined variables export automatically:

set -a
source "$HOME/devops-lab/config/app.env"
set +a

Use this only for a trusted file containing intentional shell-compatible assignments. Avoid sourcing arbitrary .env files downloaded from somewhere or writable by untrusted users.

B. A safer approach for a simple Bash script

For a script that needs only a few settings, it is often clearest to load the trusted config file and validate each required variable:

#!/usr/bin/env bash
set -Eeuo pipefail

CONFIG_FILE="$HOME/devops-lab/config/app.env"

if [[ ! -r "$CONFIG_FILE" ]]; then
    echo "ERROR: Config file is missing or unreadable" >&2
    exit 2
fi

source "$CONFIG_FILE"

: "${APP_ENV:?APP_ENV is required}"
: "${APP_NAME:?APP_NAME is required}"

printf 'Starting %s in %s mode\n' "$APP_NAME" "$APP_ENV"

The expressions ${APP_ENV:?message} and ${APP_NAME:?message} stop execution if the variable is unset or empty. This prevents an application from silently running with missing configuration.

This is a trusted shell configuration pattern—not a general-purpose parser for every .env format.

C. How to handle a .env file in Python

Python does not automatically read .env files. A common pattern is to use a library such as python-dotenv, installed into the application's virtual environment, and then read variables through os.environ.

Example application code:

import osapp_env = os.environ.get("APP_ENV", "development")log_level = os.environ.get("LOG_LEVEL", "INFO")print(f"Environment: {app_env}")print(f"Log level: {log_level}")

This reads the environment passed to the Python process. It does not itself load a .env file.

If your project uses python-dotenv, a trusted local development setup might use:

from dotenv import load_dotenvload_dotenv()

Install and pin dependencies according to your project's normal process. For production, explicit service configuration or a dedicated secrets manager is often preferable to relying on an implicit .env lookup.

6. Secrets: passwords, tokens and API keys

A secret is a value that must be protected against unauthorized access. Examples include:

  • Database passwords
  • API tokens
  • SSH private keys
  • Cloud credentials
  • Signing keys

Configuration and secrets are related, but they are not the same. APP_ENV=staging is usually ordinary configuration; DATABASE_PASSWORD is sensitive.

Recommended handling

Do

  • Restrict config-file access with appropriate ownership and permissions.
  • Use a secret manager or approved deployment mechanism when available.
  • Keep secrets out of Git, logs, screenshots, and support tickets.
  • Rotate a secret if it has been exposed.

Don't

  • Hardcode real credentials in scripts or source repositories.
  • Run cat on a secret file and paste the result into a public issue.
  • Print all environment variables in production diagnostics.
  • Enable shell tracing with set -x when commands may expose secrets.

A. Protect a file containing secrets

If your deployment process requires a local secret file, use the approved service account and deployment procedures. For a simple private file owned by the current user:

chmod 600 "$HOME/devops-lab/config/app.env"

Verify ownership and permissions:

ls -l "$HOME/devops-lab/config/app.env"
namei -l "$HOME/devops-lab/config/app.env"

namei -l helps you inspect permissions on each directory in a path. Remember, file permissions alone are not a complete secret-management solution.

B. Why environment variables are not a perfect secret vault

Environment variables can be convenient for passing secrets to applications, but they are not automatically secret. Depending on the system, user permissions, process settings, and debugging tools, environment values may be visible to the process itself, privileged users, or other authorized inspection tools.

For production credentials, prefer an approved secrets-management mechanism. If environment variables are used, restrict access to the process, host, service account, logs, and deployment configuration.

C. Keep secrets out of Git

Check a repository's status before committing:

git status --short

A typical .gitignore entry might be:

.env
.env.*
!.env.example

Use .env.example for placeholder names only, such as:

APP_ENV=staging
DATABASE_URL=
API_TOKEN=

This pattern is only a starting point. Review your repository's actual ignore rules and do not assume that adding a file to .gitignore removes it from Git history if it was already committed. If a real secret was committed, revoke or rotate it and follow your incident process.

7. Configuration with cron

In Lesson 16, you scheduled your health-check script. Cron jobs often fail because they don't receive the same environment as your interactive terminal.

A typical crontab might define:

SHELL=/bin/bash
PATH=/usr/local/bin:/usr/bin:/bin

Then use absolute paths for the script and its dependencies.

For example:

*/15 * * * * /usr/bin/bash /home/YOUR_USER/devops-lab/health_check.sh cron 80 >> /home/YOUR_USER/devops-lab/logs/health-check.log 2>&1

Replace YOUR_USER with the actual home-directory path. Verify paths on your system before installing the job.

What if the script needs APP_ENV?

For a non-secret setting, you can define it in the crontab:

APP_ENV=staging

Then the job can inherit it. Or pass it explicitly to a command:

*/15 * * * * APP_ENV=staging /usr/bin/bash /home/YOUR_USER/devops-lab/health_check.sh cron 80 >> /home/YOUR_USER/devops-lab/logs/health-check.log 2>&1

Use the actual path and only use this syntax for a variable the script or application is designed to read.

For a trusted shell config file, a script can load it itself. That makes the dependency explicit and easier to test than assuming cron will read ~/.bashrc.

Do not put production passwords directly into a crontab. Crontabs may be readable by administrators and can be exposed through backups or diagnostics. Use an approved secrets mechanism and restrictive permissions.

8. Configuration for systemd services

For a long-running application, systemd can supply environment variables to the service.

An illustrative unit fragment:

[Service]
Environment="APP_ENV=production"
Environment="LOG_LEVEL=INFO"

These are non-secret settings. After editing a unit file:

sudo systemctl daemon-reload
sudo systemctl restart myapp
sudo systemctl status myapp
sudo journalctl -u myapp -n 50 --no-pager

daemon-reload reloads systemd's unit definitions. Restarting a service is a separate operation.

What about EnvironmentFile=?

A service can refer to a file:

[Service]
EnvironmentFile=/etc/myapp/myapp.env

Create and protect that file through your approved administrative process. Confirm that the service can read it and that it contains the expected syntax. systemd's environment-file format is not identical to every framework's .env format.

For example, a service-specific configuration file may contain non-secret values such as:

APP_ENV=production
LOG_LEVEL=INFO

If a secret is involved, consider systemd credential facilities or your organization's secrets manager rather than treating a general environment file as a vault. Exact options depend on your Ubuntu and systemd versions.

9. Realistic DevOps case study: works manually, fails in cron

Imagine your journal delivery validation team runs a health-check script every 15 minutes. When you execute it from the terminal, it works. When cron runs it, the log reports:

ERROR: APP_ENV is required

Or the application reports:

ERROR: DATABASE_URL is missing

Step 1 — Identify the execution context

Run the health check manually:

bash "$HOME/devops-lab/health_check.sh" cron 80

Check whether the variable exists in your current shell:

printf 'APP_ENV=%s\n' "${APP_ENV:-not set}"

If it prints not set, the script may have been relying on an environment variable that was never defined.

Step 2 — Confirm the script's requirements

Inspect the script without exposing credentials:

grep -nE 'APP_ENV|DATABASE_URL|CONFIG_FILE' \
  "$HOME/devops-lab/health_check.sh"

Review the relevant code. Does the script expect an exported variable? Does it load a config file? Does it validate missing settings?

Avoid printing actual secret values during this investigation.

Step 3 — Choose the right fix

For this lesson's lab, we'll use a non-secret APP_ENV setting. Create a trusted configuration file:

mkdir -p "$HOME/devops-lab/config"
chmod 700 "$HOME/devops-lab/config"
nano "$HOME/devops-lab/config/app.env"

Add:

APP_ENV=staging
APP_NAME=journal-validator

Then protect the file:

chmod 600 "$HOME/devops-lab/config/app.env"

In the script, load it explicitly and validate required settings:

CONFIG_FILE="$HOME/devops-lab/config/app.env"

if [[ ! -r "$CONFIG_FILE" ]]; then
    echo "ERROR: Configuration file missing or unreadable" >&2
    exit 2
fi

source "$CONFIG_FILE"
: "${APP_ENV:?APP_ENV is required}"

This example assumes the file is trusted shell-compatible configuration. If the application needs the values in a child process, export the specific variables:

export APP_ENV APP_NAME

If the actual issue is a missing database credential, do not invent a password or paste one into the script. Retrieve the credential through your approved secret-delivery mechanism and ensure the application can access it securely.

Step 4 — Test before changing the schedule

bash -n "$HOME/devops-lab/health_check.sh"
bash "$HOME/devops-lab/health_check.sh" cron 80

bash -n checks shell syntax; it does not guarantee the script will run correctly. Execute the script and inspect its exit status:

bash "$HOME/devops-lab/health_check.sh" cron 80
echo "Exit status: $?"

For the Lesson 15 health-check script, the expected convention was 0 for passing checks, 1 for a failed check, and 2 for an invalid threshold or configuration. Confirm that the current version still follows that convention.

Step 5 — Verify the cron job

Inspect your crontab:

crontab -l

Review the configured absolute paths, output redirection, lock command if used, and any required non-secret environment variables. After the next scheduled run:

tail -n 50 "$HOME/devops-lab/logs/health-check.log"

Check the log and the script's actual results—not merely whether cron launched the command. Cron does not automatically alert you for every nonzero exit status.

Incident report example

Incident: Scheduled health check reports missing configuration.

Impact: Automated monitoring may not report the service's condition reliably.

Root cause: The cron process did not inherit a variable that was available in the interactive shell.

Resolution: Load trusted configuration explicitly, validate required variables, test manually, then verify the scheduled run.

Prevention: Document required settings, protect configuration files, and alert on failed scheduled jobs.

Five rules to remember

  1. Shell variables are not automatically exported.
  2. Cron has its own execution environment. Use explicit configuration and absolute paths.
  3. A .env file is not automatically loaded by every application.
  4. Protect secrets and avoid printing them into logs or tickets.
  5. Validate configuration before running production workloads.
