Production practices

In Lesson 15, we learned the fundamentals of Bash scripting. In Lesson 16, we scheduled scripts with cron. In Lesson 19, we learned how to troubleshoot Linux servers systematically.

Now we will combine those skills to build reliable automation that can safely run unattended on a production server.

We'll use realistic examples from application support, including a journal validation service that processes delivery packages and must report failures clearly without damaging data.

1. What makes a script production-ready?

A basic script may work when run manually but fail when executed by cron, systemd, or a deployment pipeline. A production script must handle those situations deliberately.

The production automation workflow

Start

CLI arguments, scheduler, or service manager

Validate inputs and prerequisites

Arguments, files, commands, permissions

Run the task safely

Functions, logging, locking, error handling

Success

Verify result and exit 0

Failure

Log the cause and return nonzero

A good production script should:

  • Fail clearly when an essential prerequisite is missing.
  • Return meaningful exit codes so other tools can detect success or failure.
  • Log enough information to troubleshoot without exposing secrets.
  • Clean up temporary files when appropriate.
  • Avoid running the same job concurrently when that could corrupt or duplicate work.
  • Be safe to run again when possible.
  • Verify that the intended outcome actually happened.

2. Exit codes: how Linux scripts report success and failure

Every command returns an exit status. By convention, 0 means success and a nonzero value means failure or another condition.

Exit code Typical meaning
0 Success
1 General failure or a failed check, depending on the command
2 Commonly incorrect usage or invalid arguments, depending on the command
Other nonzero values Command-specific failure

Inspect the previous command's status with:

ls /etc
echo "$?"

If the command succeeds, the second command will usually print 0. Be careful: $? refers to the most recently executed command, so running echo "$?" again reports the status of echo, not the original command.

Prefer direct error checks

if cp source.txt backup.txt; then
    echo "Copy succeeded"
else
    echo "Copy failed"
fi

This is generally better than running the command and checking $? later, because it tests the intended command directly.

You can also combine commands:

mkdir -p /tmp/devops-lab && echo "Directory ready"

The second command runs only if the first succeeds.

some_command || echo "The command failed"

The message runs if some_command returns nonzero.

Important: Exit code 1 does not have one universal meaning. For example, grep returns 1 when it finds no matching lines, which may be a normal result rather than an operational failure.

3. set -Eeuo pipefail: useful, but not magic

A common Bash script starts like this:

#!/usr/bin/env bash
set -Eeuo pipefail

Let's understand each option.

-e — exit on many unhandled failures

Bash exits when certain commands fail in contexts where their status is not being tested. This catches many mistakes, but it does not catch every failure.

-E — inherit ERR traps

Allows an ERR trap to be inherited in more contexts, including functions and subshell environments, subject to Bash's trap rules.

-u — catch unset variables

Using an unset variable can terminate the script. Use defaults when a variable is optional: ${APP_ENV:-staging}.

pipefail — detect pipeline failures

A pipeline such as producer | grep something can fail even when its last command succeeds. pipefail makes the pipeline's status reflect the rightmost failing command, or zero if all commands succeed.

Caveats you must understand

set -e has exceptions. It behaves differently in conditions such as if, while, until, parts of &&/|| lists, and some pipeline/function contexts. Do not rely on it as your only error-handling strategy.

For example:

#!/usr/bin/env bash
set -Eeuo pipefail

if grep -q "ERROR" app.log; then
    echo "Errors found"
else
    echo "No matching errors"
fi

Here, a grep status of 1 means no matching line was found; it is handled intentionally.

Also remember:

  • ((count++)) can return status 1 when the expression's value is zero. Under set -e, this can unexpectedly stop a script. Prefer ((count += 1)) when incrementing from zero, or use count=$((count + 1)).
  • A failed command inside a conditional may be intentional. Handle it explicitly.
  • set -e is not a substitute for checking important operations and verifying the final result.

4. Functions: make scripts easier to maintain

Functions package reusable logic into named blocks.

log_info() {
    printf '[INFO] %s\n' "$*"
}

log_error() {
    printf '[ERROR] %s\n' "$*" >&2
}

check_directory() {
    local directory="$1"

    if [[ -d "$directory" ]]; then
        log_info "Directory exists: $directory"
    else
        log_error "Directory missing: $directory"
        return 1
    fi
}

Use them like this:

check_directory "/var/log"
log_info "Check complete"

Key ideas:

  • local keeps a variable scoped to the function.
  • "$1" is the first argument passed to the function.
  • return 0 indicates success; return 1 indicates failure.
  • "$*" is useful for joining arguments into one message, while "$@" preserves individual arguments. Avoid using a joined message as an argument list.

A function should usually do one well-defined job: validate input, check a service, write a log message, or clean up a resource.

5. Command-line arguments and input validation

Scripts often need to accept different services, thresholds, directories, or environments without editing the code each time.

Example:

./health_check.sh cron 80

In the script:

Variable Meaning Example
$0 Script name ./health_check.sh
$1 First argument cron
$2 Second argument 80
$# Number of arguments 2
"$@" All arguments, individually preserved cron and 80

Validate before acting

Suppose a script accepts a disk usage threshold. We should reject invalid values such as -5, abc, or 150.

if [[ $# -ne 2 ]]; then
    echo "Usage: $0 SERVICE_NAME DISK_THRESHOLD" >&2
    exit 2
fi

service="$1"
threshold="$2"

if [[ ! "$threshold" =~ ^[0-9]+$ ]]; then
    echo "Error: threshold must be a whole number" >&2
    exit 2
fi

if (( threshold < 1 || threshold > 100 )); then
    echo "Error: threshold must be between 1 and 100" >&2
    exit 2
fi

This validates the number of arguments, numeric format, and permitted range before the script does any work.

For more robust production scripts, also validate the service name against an approved list instead of accepting arbitrary input.

6. Logging: make unattended scripts diagnosable

When a command fails in a terminal, you can see the error. When the same command runs at 2 AM under cron, nobody may be watching.

Logging creates a record of what happened.

A simple logging function

log() {
    local level="$1"
    shift
    printf '%s [%s] %s\n' \
        "$(date '+%Y-%m-%d %H:%M:%S%z')" \
        "$level" "$*"
}

log INFO "Health check started"
log WARN "Disk usage is approaching the limit"
log ERROR "Service is inactive"

For scripts, it is useful to distinguish:

  • INFO — normal progress.
  • WARN — something needs attention.
  • ERROR — a check or operation failed.

Write errors to standard error where appropriate:

printf 'ERROR: configuration missing\n' >&2

Redirect output when scheduling

./health_check.sh cron 80 >> health-check.log 2>&1
  • >> appends standard output.
  • 2>&1 sends standard error to the same destination as standard output.
  • The order matters: > file 2>&1 sends both streams to the file; 2>&1 > file does not do the same thing.

In production, choose a log location the script's execution user can write to, and configure log rotation so the file cannot grow indefinitely. Avoid logging passwords, tokens, private keys, or sensitive dataset contents.

7. Traps and cleanup

A trap lets a script respond to certain signals or shell events. It is useful when a script creates temporary files, acquires resources, or needs to report unexpected failures.

cleanup() {
    if [[ -n "${TEMP_FILE:-}" && -f "$TEMP_FILE" ]]; then
        rm -f -- "$TEMP_FILE"
    fi
}

trap cleanup EXIT

The EXIT trap runs when the shell exits, including after many failures.

A failure-reporting trap can also be useful:

on_error() {
    local status=$?
    printf 'ERROR: script failed near line %s (exit %s)\n' \
        "${BASH_LINENO[0]:-unknown}" "$status" >&2
    exit "$status"
}

trap on_error ERR

With set -E, the ERR trap is inherited in more contexts, but its behavior still has exceptions. Do not assume it runs for every unsuccessful command.

Best practice: use traps for cleanup and diagnostic context, but use explicit if checks for important operations. An error trap should not hide the original exit status or pretend that the operation succeeded.

Signals also have different meanings:

  • INT — often triggered by Ctrl+C.
  • TERM — a termination request.
  • EXIT — shell exit event, not a Unix signal.
  • KILL — cannot be caught; the script cannot perform cleanup after SIGKILL.

8. Safe temporary files

Avoid hardcoding predictable temporary filenames such as /tmp/report.tmp. Another process might create that name first, creating a race or security risk.

Use mktemp:

TEMP_FILE=$(mktemp) || {
    echo "Could not create temporary file" >&2
    exit 1
}

trap 'rm -f -- "$TEMP_FILE"' EXIT

printf 'Sample report\n' > "$TEMP_FILE"

For a temporary directory:

TEMP_DIR=$(mktemp -d) || exit 1
trap 'rm -rf -- "$TEMP_DIR"' EXIT

The recursive deletion is safe here only because TEMP_DIR is the path returned by mktemp -d and is owned by this script. Keep that variable controlled; never build a deletion path from unchecked user input.

For sensitive or production data, choose an appropriate directory and permissions, and ensure cleanup does not delete files the script does not own.

9. Idempotency: make reruns safe

Idempotency means that repeating an operation produces the same intended end state rather than causing repeated unwanted effects.

For example, creating a directory this way is idempotent:

mkdir -p /opt/myapp/logs

Running it repeatedly leaves the directory present.

This is less safe:

echo "production" >> /opt/myapp/environment.txt

Every run adds another line.

A safer way to enforce a desired configuration is:

printf '%s\n' 'production' > /opt/myapp/environment.txt

This overwrites the file, so only use it when replacing the entire file is intended. For important configuration, validate the content and use an atomic update pattern rather than exposing a partially written file.

Idempotency does not mean every action is harmless to repeat. Sending emails, processing a payment, deleting a dataset, or rerunning a validation job may have side effects. Those operations need application-level deduplication, transaction handling, or a job identifier.

10. Prevent overlapping runs with flock

If cron starts a new validation job every 15 minutes but the previous run takes 25 minutes, two jobs may compete for the same files or database.

A lock can prevent concurrent execution on the same machine:

/usr/bin/flock -n /tmp/journal-validator.lock \
    /opt/myapp/bin/run_validation.sh

With -n, a second invocation exits rather than waiting if the lock is already held.

Check the installed path with:

command -v flock

The lock is associated with the open file descriptor, not simply the existence of a file. Keep the lock path consistent across all invocations, and ensure the execution user can access it. flock is a single-host coordination mechanism, not a distributed lock across multiple servers.

11. Build a realistic production-style health-check script

We'll create a read-only health check that:

  1. Validates its arguments.
  2. Confirms required commands are available.
  3. Checks root filesystem usage against a threshold.
  4. Checks whether a specified systemd service is active.
  5. Logs each result.
  6. Returns a meaningful exit code.
  7. Cleans up temporary resources.

It will not restart services, delete logs, or make configuration changes. That is intentional: monitoring should normally observe first, and remediation should be a separately reviewed action.

Step A — Create a lab directory

mkdir -p "$HOME/devops-lab"
cd "$HOME/devops-lab"
nano health_check.sh

Paste this complete script:


#!/usr/bin/env bash
set -Eeuo pipefail

# Usage: ./health_check.sh SERVICE_NAME DISK_THRESHOLD

TEMP_FILE=""

log() {
    local level="$1"
    shift
    printf '%s [%s] %s\n' \
        "$(date '+%Y-%m-%d %H:%M:%S%z')" \
        "$level" "$*"
}

cleanup() {
    if [[ -n "${TEMP_FILE:-}" && -f "$TEMP_FILE" ]]; then
        rm -f -- "$TEMP_FILE"
    fi
}

on_error() {
    local status=$?
    log ERROR "Unexpected failure near line ${BASH_LINENO[0]:-unknown}; exit=${status}" >&2
    exit "$status"
}

trap cleanup EXIT
trap on_error ERR

usage() {
    printf 'Usage: %s SERVICE_NAME DISK_THRESHOLD(1-100)\n' "$0" >&2
    exit 2
}

# 1. Validate arguments
[[ $# -eq 2 ]] || usage

SERVICE="$1"
THRESHOLD="$2"

if [[ ! "$SERVICE" =~ ^[a-zA-Z0-9_.@-]+$ ]]; then
    log ERROR "Invalid service name format"
    exit 2
fi

if [[ ! "$THRESHOLD" =~ ^[0-9]+$ ]]; then
    log ERROR "Disk threshold must be an integer"
    exit 2
fi

if (( THRESHOLD < 1 || THRESHOLD > 100 )); then
    log ERROR "Disk threshold must be between 1 and 100"
    exit 2
fi

# 2. Verify prerequisites
for command_name in date df awk systemctl; do
    if ! command -v "$command_name" >/dev/null 2>&1; then
        log ERROR "Required command not found: $command_name"
        exit 2
    fi
done

log INFO "Health check started: service=$SERVICE threshold=${THRESHOLD}%"

# 3. Check root filesystem usage
TEMP_FILE=$(mktemp) || {
    log ERROR "Unable to create temporary file"
    exit 1
}

if ! df -P / > "$TEMP_FILE"; then
    log ERROR "Unable to read root filesystem usage"
    exit 1
fi

DISK_USAGE=$(awk 'NR == 2 { gsub(/%/, "", $5); print $5 }' "$TEMP_FILE")

if [[ ! "$DISK_USAGE" =~ ^[0-9]+$ ]]; then
    log ERROR "Could not parse disk usage"
    exit 1
fi

if (( DISK_USAGE >= THRESHOLD )); then
    log ERROR "Root filesystem usage is ${DISK_USAGE}% (threshold ${THRESHOLD}%)"
    DISK_FAILED=1
else
    log INFO "Root filesystem usage is ${DISK_USAGE}%"
    DISK_FAILED=0
fi

# 4. Check the service state
if systemctl is-active --quiet "$SERVICE"; then
    log INFO "Service $SERVICE is active"
    SERVICE_FAILED=0
else
    log ERROR "Service $SERVICE is not active"
    SERVICE_FAILED=1
fi

# 5. Return a result for cron/systemd/monitoring
if (( DISK_FAILED != 0 || SERVICE_FAILED != 0 )); then
    log ERROR "Health check FAILED"
    exit 1
fi

log INFO "Health check PASSED"
exit 0

Save in nano using Ctrl+O, Enter, then Ctrl+X.

Step B — Set permissions and validate syntax

chmod 750 "$HOME/devops-lab/health_check.sh"
bash -n "$HOME/devops-lab/health_check.sh"

bash -n checks syntax without running the script. No output usually means the syntax check passed.

Check the script's interpreter and permissions:

head -n 1 "$HOME/devops-lab/health_check.sh"
ls -l "$HOME/devops-lab/health_check.sh"

Step C — Run the script

On a typical Ubuntu system with cron installed and active:

"$HOME/devops-lab/health_check.sh" cron 80
echo "Exit code: $?"

Other service names can be tested too, for example:

"$HOME/devops-lab/health_check.sh" ssh 80

Test invalid inputs:

"$HOME/devops-lab/health_check.sh" cron abc
echo "Exit code: $?"

"$HOME/devops-lab/health_check.sh" cron 150
echo "Exit code: $?"

Expected behavior:

  • Exit 0: both checks passed.
  • Exit 1: a health check failed or an operational check could not complete.
  • Exit 2: invalid arguments or a required command is missing.

A script may report exit 1 when a service is inactive even if the script itself is functioning correctly. The exit code communicates the health-check result to the scheduler or monitoring system.

Limitations to understand: this example checks the root filesystem, not every mounted filesystem. systemctl is-active verifies service state, not whether an application endpoint, database, or business operation is healthy. A production deployment should add checks relevant to the actual service.

12. Integrate with cron

Cron is suitable for periodic checks. First confirm the script works manually before scheduling it.

Step A — Find the real paths

command -v bash
command -v flock
printf '%s\n' "$HOME"

Step B — Create a log directory

mkdir -p "$HOME/devops-lab/logs"
chmod 700 "$HOME/devops-lab/logs"

Step C — Edit your user crontab

crontab -e

Add this line, replacing /home/YOUR_USER with the actual home directory:

*/15 * * * * /usr/bin/flock -n /tmp/health-check.lock /usr/bin/bash /home/YOUR_USER/devops-lab/health_check.sh cron 80 >> /home/YOUR_USER/devops-lab/logs/health-check.log 2>&1

This runs the check every 15 minutes, skipping a run if the lock is already held, and appending output to a log.

Then verify:

crontab -l
tail -n 30 "$HOME/devops-lab/logs/health-check.log"

Remember, cron usually has a minimal environment. Use absolute paths, explicitly set required environment variables, and test using the same account that owns the crontab. The script itself needs no root privileges for this particular example.

13. Integrate with systemd

A systemd service is a good fit for running a script on demand or as part of an operational workflow. For periodic scheduling, a systemd timer can be preferable to cron when you want systemd-managed scheduling and logging.

For this read-only health check, we'll use a oneshot service.

Create a unit:

sudo nano /etc/systemd/system/health-check.service

Example unit — replace /home/YOUR_USER with the correct absolute path:


[Unit]
Description=Application and disk health check
After=local-fs.target

[Service]
Type=oneshot
User=YOUR_USER
ExecStart=/usr/bin/bash /home/YOUR_USER/devops-lab/health_check.sh cron 80

Then validate and run:

sudo systemd-analyze verify /etc/systemd/system/health-check.service
sudo systemctl daemon-reload
sudo systemctl start health-check.service
sudo systemctl status health-check.service
sudo journalctl -u health-check.service -n 50 --no-pager

Replace YOUR_USER in both the unit and the path before running. The service account must be able to read and execute the script and access the needed commands. Type=oneshot means systemd runs the check and waits for it to finish; it is not a continuously running daemon.

A periodic systemd timer could be added separately. Do not enable both cron and a timer for the same job unless duplicate execution is intended and controlled.

Cron vs systemd

Feature Cron systemd service/timer
Main use Scheduled commands Managed services and schedules
Logs Redirect output or use system logging Available through the journal
Environment Minimal Explicit unit environment and execution settings
Dependencies Mostly handled in script Can express unit dependencies
Missed runs Usually not replayed automatically Timers can support catch-up behavior with Persistent=true
Best fit Simple recurring jobs Managed server tasks and service lifecycle
