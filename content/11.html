In this lesson, you’ll learn how Linux services work, how to manage them using systemctl, how to investigate failed services, and how to make applications start automatically when a server boots.

1. What is a Linux service?

Imagine your Ubuntu server hosts a website. The website needs a web server such as Nginx to run in the background, even when nobody is logged into the server.

A service is a program or system capability that runs to provide a function. Many services operate in the background and are managed by systemd, the service manager used by most modern Ubuntu installations.

Examples include:

  • ssh — remote server access.
  • nginx — web serving and reverse proxy.
  • cron — scheduled tasks.
  • docker — container management, when installed.
  • postgresql — database service, when installed.

A service is not necessarily a network server. It might perform scheduled jobs, manage hardware, or support other system processes.

Think of systemd as a coordinator. It starts configured services, tracks their states, manages dependencies, and records information that can help you troubleshoot failures.

The command-line interface you’ll use most often is:

systemctl

A service commonly has a unit name ending in .service, such as nginx.service. For many commands, the .service suffix can be omitted, so systemctl status nginx is equivalent to checking nginx.service.

3. Check whether a service is running

Before changing anything on a server, inspect its current state.

systemctl status nginx

If Nginx is installed, the output may include information such as:

nginx.service - A high performance web server
     Loaded: loaded (...)
     Active: active (running)
   Main PID: 1234 (nginx)

The PID and paths shown above are illustrative; your output will differ.

Understand the important fields

Field Meaning
Loaded Whether systemd found and loaded the unit definition
Active Current high-level state of the unit
Main PID Main process ID, when applicable
enabled Configured to start automatically through its enablement links
disabled Not enabled for automatic startup in the usual way

A service can be running but disabled for automatic startup. It can also be enabled but currently stopped.

Useful inspection commands

systemctl is-active nginx
systemctl is-enabled nginx
systemctl list-units --type=service --state=running
systemctl --failed
  • is-active checks the current active state.
  • is-enabled checks its startup enablement configuration.
  • list-units lists units currently loaded into systemd's view, filtered here to running services.
  • --failed lists units systemd currently considers failed.

DevOps habit: status first, diagnosis second, changes third.

4. Start, stop, restart, and reload services

These are the core commands you’ll use during deployment and incident troubleshooting.

Operation Command What it does
Start sudo systemctl start nginx Starts the service now
Stop sudo systemctl stop nginx Stops the service now
Restart sudo systemctl restart nginx Stops and starts the service
Reload sudo systemctl reload nginx Asks the service to reload its configuration, if supported
Check status systemctl status nginx Shows current state and recent status information

A restart can interrupt active connections. Prefer a reload when the application supports it and you only need to apply a configuration change.

Important safety rule for SSH

If you are connected to a remote Ubuntu server through SSH, stopping or restarting the SSH service can interrupt access or prevent future logins if the service fails to come back.

Before changing SSH:

  1. Confirm you have console or another recovery route if possible.
  2. Validate the SSH configuration with sudo sshd -t when the OpenSSH server is installed.
  3. Review the planned change and keep an existing session open while testing a second connection.
  4. Do not stop a remote-access service casually on a production machine.

Also, the service name on Ubuntu is often ssh, while the server daemon executable is sshd.

5. Enable services at boot

Starting a service and enabling it are different operations.

  • start affects the service now.
  • enable configures it to start automatically through the system's boot dependency configuration.
  • disable removes that automatic enablement.
  • enable --now enables it and attempts to start it immediately.

Examples:

sudo systemctl enable nginx
sudo systemctl disable nginx
sudo systemctl enable --now nginx
sudo systemctl disable --now nginx

The last command disables automatic startup and also stops the service now. Use it only when both actions are intended.

To inspect enablement:

systemctl is-enabled nginx

To see what is enabled:

systemctl list-unit-files --type=service --state=enabled

Visual: current state vs. boot configuration

A service can be running but disabled, or stopped but enabled. Always check both dimensions.

6. Read service logs with journalctl

When a service fails, systemctl status gives a useful starting point. For more details, use journalctl, which reads the systemd journal.

sudo journalctl -u nginx

Useful variations:

sudo journalctl -u nginx -n 50
sudo journalctl -u nginx --since "30 minutes ago"
sudo journalctl -u nginx -f
sudo journalctl -u nginx -b
sudo journalctl -p err --since today
Command Purpose
-u nginx Filter logs for the Nginx unit
-n 50 Show the latest 50 entries
--since Limit the time range
-f Follow new log entries live
-b Show entries from the current boot
-p err Filter to error priority and more severe priorities

Press Ctrl+C to stop following logs.

For an incident, a practical sequence is:

systemctl status nginx --no-pager
sudo journalctl -u nginx --since "15 minutes ago" --no-pager

Start with a narrow time window and expand it if necessary. Avoid dumping huge logs into terminals or tickets without filtering sensitive information.

7. Service failures: understand the common states

active (running)

The service is currently running. This alone does not prove that the application is healthy or reachable.

inactive (dead)

The service is not currently running. This may be expected for a stopped or on-demand service.

failed

The service or unit entered a failed state. Examine logs, configuration, dependencies and exit information.

activating

The service is still in its startup process. Check its startup logs if it remains there unexpectedly.

After resolving a failure, you may want to clear the recorded failed state:

sudo systemctl reset-failed nginx

This resets systemd's failed-state tracking; it does not fix the underlying problem or start the service by itself.

8. Diagnose service startup failures

Use a consistent troubleshooting workflow instead of repeatedly restarting the service.

1. Inspect status

systemctl status nginx

2. Read logs

journalctl -u nginx -n 50

3. Test configuration

sudo nginx -t

4. Fix the specific cause

Configuration, permissions, port conflict, dependencies or missing files

5. Validate and verify

Reload or restart as appropriate, then check status and application behavior

Other useful diagnostic commands:

systemctl list-dependencies nginx
systemctl cat nginx
sudo ss -lntp
df -h
free -h

These can help investigate dependencies, the unit definition, occupied TCP ports, disk space and memory.

If nginx is not installed, its unit may not exist. Check installation and package availability rather than assuming every service name is present.

9. Understand service unit files

Systemd uses unit files to describe how services are started and managed.

Inspect a service's effective unit definition with:

systemctl cat nginx

Common unit-file locations include:

  • /usr/lib/systemd/system/ or /lib/systemd/system/ — commonly used for package-provided units, depending on the system's layout.
  • /etc/systemd/system/ — commonly used for administrator-created units and overrides.

Do not edit a package-provided unit file directly unless you have a specific reason. Administrator overrides are generally easier to maintain.

Example: a custom Python application

Suppose you have a Python application located at /opt/myapp/app.py, and its virtual environment is /opt/myapp/venv. You want systemd to run it as a service.

A unit file might look like this:

[Unit]
Description=My Python Web Application
After=network.target

[Service]
Type=simple
User=myapp
WorkingDirectory=/opt/myapp
ExecStart=/opt/myapp/venv/bin/python /opt/myapp/app.py
Restart=on-failure

[Install]
WantedBy=multi-user.target

This is an example template, not a ready-to-run configuration. The myapp user, directories, virtual environment and application must exist, and the Python application must be designed to run correctly in the foreground.

What the sections mean:

Section Purpose
[Unit] Describes the unit and its relationships
[Service] Defines how the program runs and how failures are handled
[Install] Defines how the unit can be enabled

Restart=on-failure asks systemd to restart the process when it exits unsuccessfully, subject to systemd's restart limits and other settings. It is not a substitute for application health monitoring.

Install a custom service

After placing a validated unit file at /etc/systemd/system/myapp.service:

sudo systemd-analyze verify /etc/systemd/system/myapp.service
sudo systemctl daemon-reload
sudo systemctl enable --now myapp
systemctl status myapp
sudo journalctl -u myapp -n 50 --no-pager

Why daemon-reload? It tells systemd to reload unit definitions after you create or modify unit files. It does not restart every running service.

For a configuration file belonging to an existing application, use that application's own validation and reload procedure instead. Editing a service unit and editing an application's configuration are different operations.

10. Real-world DevOps case study: deployment service keeps failing

Scenario

Your team deploys a Python web application on Ubuntu. The deployment finishes, but the application service fails to start. The deployment dashboard shows an error, and the site is unavailable.

The service is called myapp.service.

Step 1 — Inspect the service

systemctl status myapp --no-pager

Check the unit's state, exit status, and recent error messages.

Step 2 — Read the logs

sudo journalctl -u myapp --since "15 minutes ago" --no-pager

Look for a missing executable, missing configuration, permission denial, import error or port conflict.

Step 3 — Check the executable and working directory

systemctl cat myapp
ls -l /opt/myapp/venv/bin/python
ls -ld /opt/myapp

Confirm that paths in ExecStart and WorkingDirectory exist and that the configured service user has appropriate access.

Step 4 — Fix the actual cause

If the virtual environment is missing, repair the deployment or recreate it using the project's documented setup. If permissions are wrong, fix the specific ownership or access issue rather than granting broad permissions.

Step 5 — Verify recovery

sudo systemctl restart myapp
systemctl is-active myapp
sudo journalctl -u myapp -n 30 --no-pager

Then test the application's health endpoint or expected behavior. An active service is not proof that the website works end-to-end.

What if you changed the service unit?

If the issue was caused by a change to /etc/systemd/system/myapp.service, run sudo systemctl daemon-reload before starting or restarting the service so systemd uses the updated unit definition.

Lessons from the incident

  • Don't assume a failed deployment means the package is missing.
  • Check logs before making changes.
  • Validate paths and run the application with the intended service account.
  • Avoid running the application as root unless its design specifically requires it.
  • Verify both the systemd service and the application itself after recovery.

The five rules to remember

Inspect before changing. Use systemctl status and journalctl to collect evidence.

Know the difference between runtime and boot. start is not enable.

Validate before restarting. Use the application's configuration test when available.

Reload systemd after unit-file changes. daemon-reload is different from restarting a service.

Verify application health. A running process does not necessarily mean the application works.
