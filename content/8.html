Linux for DevOps — Module 1, Lesson 7

Linux processes and jobs: ps, top, pgrep, kill, jobs, bg, fg, and nohup

Beginner

Hands-on lab

DevOps troubleshooting

Every application running on Linux uses one or more processes. When a website becomes slow, a deployment hangs, or a background script stops after you disconnect from SSH, understanding processes helps you investigate and respond safely.

In this lesson, you'll learn to inspect running programs, understand process IDs and signals, control terminal jobs, and run commands that can continue after a terminal session ends.

1. What is a process?

A process is a running instance of a program.

For example, when a Linux server runs Nginx, Python, a shell script, or a database, the operating system tracks the corresponding processes.

Program on disk

Example: app.py

Running process

Has a PID, memory, state, and resource usage

PID

Process identifier

Memory

RAM usage

CPU

Processing activity

A program is the code or executable stored on disk. A process is a running instance of that program. The same program can have multiple processes.

What is a PID?

PID stands for Process ID. Linux assigns a numeric identifier to each process.

Example:

PID    COMMAND
1      systemd
842    nginx
1095   python3
1270   bash

These numbers are illustrative. Actual PIDs vary between systems and change as processes start and stop.

A process also has a parent process ID (PPID), which helps show how processes were started.

2. Understand the process tree

Processes can start other processes. The resulting parent-child relationships form a process tree.

To see processes and their parents, use:

ps -ef

Or show a process tree:

ps -ef --forest

Some Linux variants have different ps options, but these are commonly available on Ubuntu.

3. Inspect processes with ps

ps means process status. It provides a snapshot of running processes.

Common commands

ps
ps -ef
ps aux
Command Purpose
ps Show processes associated with the current terminal
ps -ef Show a detailed process listing
ps aux Show processes in a BSD-style format, including resource fields
ps -u "$USER" Show processes associated with your user
ps -p 1234 -f Inspect the process with PID 1234
ps -o pid,ppid,stat,%cpu,%mem,cmd -p 1234 Select specific fields for one process

Read a ps -ef row

Example:

UID      PID  PPID  C STIME TTY      TIME CMD
deploy  1234  1100  0 10:00 pts/0  00:00:02 python3 app.py
  • UID — account running the process.
  • PID — process ID.
  • PPID — parent process ID.
  • C — CPU utilization-related field in this format.
  • STIME — process start time or date.
  • TTY — associated terminal, if any.
  • TIME — accumulated CPU time.
  • CMD — command associated with the process.

DevOps tip: Before terminating a process, inspect its PID, command, user, and parent process. A PID alone is not enough to establish that the process is safe to stop.

4. Find a process with pgrep

Suppose a server is running several programs and you want to find a Python process without reading the entire ps output.

Use pgrep:

pgrep python

To display process IDs and command names:

pgrep -a python

To search for an exact process name:

pgrep -x nginx

To find processes belonging to a particular user:

pgrep -u deploy -a

The last command lists processes belonging to deploy on systems supporting these common pgrep options.

pgrep versus ps

  • Use ps when you want a broad snapshot or more detailed process information.
  • Use pgrep when you want to find process IDs by name, user, or matching criteria.

Be careful: pgrep python can match multiple Python processes. Always inspect the results before acting on a PID.

5. Understand process states

Linux processes have states that help explain what they're doing.

State Meaning
R Running or ready to run
S Interruptible sleep, commonly waiting for an event
D Uninterruptible sleep, often waiting for I/O
T Stopped or job-control stopped
Z Zombie: exited, but its parent has not yet collected its exit status

A process in state D may not respond to ordinary termination signals until the kernel operation it is waiting for completes. A zombie process has already exited; sending it another termination signal does not solve the underlying parent-reaping issue.

Inspect states with:

ps -eo pid,ppid,stat,comm

See resource usage with top

Run:

top

top refreshes the display of processes and system resource usage.

Useful keys inside top include:

  • P — sort by CPU usage on common procps-ng versions.
  • M — sort by memory usage.
  • 1 — toggle individual CPU core displays on many versions.
  • q — quit.

What to investigate in top

High CPU

Identify which process consumes CPU, then inspect its command and logs. High CPU isn't always a fault.

High memory

Check whether memory usage is expected, increasing over time, or causing system pressure.

Long-running process

Compare its runtime and activity with the expected behavior of the application.

For a one-time snapshot, you can also run:

top -b -n 1 | head -n 20

This runs top in batch mode once and shows the first 20 lines.

6. Stop processes with kill and signals

The command kill sends a signal to a process. Despite its name, it doesn't always immediately terminate the process.

Common signals

Signal Number Meaning
SIGTERM 15 Requests orderly termination
SIGKILL 9 Forces termination; cannot be caught or ignored by the target
SIGINT 2 Interrupt, often associated with Ctrl+C in a terminal
SIGHUP 1 Hangup; some programs use it to reload configuration, but behavior is application-specific
SIGSTOP 19 on x86/Linux Stops a process; cannot be caught or ignored

Signal numbers can vary across Unix-like platforms. Signal names are more portable than hard-coded numbers.

Prefer graceful termination

For a known, disposable test process:

kill -TERM 1234

This asks PID 1234 to terminate gracefully. Replace the example PID with a verified target.

Check whether it is still running:

ps -p 1234 -f

If the process doesn't terminate, investigate why before escalating. Only when necessary and authorized, SIGKILL can be used:

kill -KILL 1234

A forced kill prevents the application from handling cleanup routines. It can leave temporary files, incomplete writes, or inconsistent application state.

Stop or continue a process

kill -STOP 1234
kill -CONT 1234
  • STOP suspends a process.
  • CONT resumes a stopped process.

These commands affect the specified process, and permission to signal it depends on user privileges and system policy.

Production safety rule: Don't terminate processes just because their names look unfamiliar or their CPU usage is high. Identify the service, check its dependencies, and use the service manager when appropriate. For example, managed Nginx services are normally controlled with systemctl, not by killing a random worker PID.

7. Terminal jobs: foreground and background

A job is a command or pipeline managed by your current shell's job-control feature. A job can contain one or more processes.

For example, if you run a long script directly in Bash, the shell waits for it in the foreground. You usually cannot enter another command in that same terminal until the script finishes or is suspended.

Foreground versus background

Foreground

The command occupies your terminal interaction.

Example: sleep 60

Background

The shell returns a prompt while the job runs.

Example: sleep 60 &

Background doesn't necessarily mean detached from the terminal. A background job may still depend on the shell, terminal input, and terminal output.

Try a harmless foreground command:

sleep 30

It waits for 30 seconds. To interrupt it, press Ctrl+C.

Now start a background job:

sleep 300 &

The shell prints a job number and often a PID, for example:

[1] 2450

Here, [1] is the shell's job number and 2450 is an example PID. They are different identifiers.

List jobs with jobs

jobs
jobs -l

Example:

[1]+  Running    sleep 300 &

jobs shows jobs managed by the current shell. It generally won't list unrelated processes launched from another terminal or by a system service.

Bring a background job to the foreground with fg

fg %1

This brings job number 1 into the foreground, if that job exists in the current shell.

To suspend a foreground job, press Ctrl+Z. The shell stops the job and returns the prompt. Then:

jobs
bg %1

bg %1 resumes job 1 in the background.

The typical workflow is:

Run a command

sleep 300

Press Ctrl+Z

Suspends the foreground job

Run bg

Resumes the suspended job in the background

Run fg

Brings the job back to the foreground

To end the test job, bring it to the foreground and press Ctrl+C, or use kill on its verified PID.

8. Run commands with nohup

Suppose you start a data-processing script over SSH. You want it to keep running even if you close the terminal session.

nohup runs a command with the hangup signal ignored. This can help with simple long-running tasks.

Example:

nohup python3 process_data.py > process.log 2>&1 &

Breakdown:

  • nohup — ignores the hangup signal for the command.
  • python3 process_data.py — the command being run.
  • > — redirects standard output to a file, replacing the file if it already exists.
  • process.log — destination for standard output.
  • 2>&1 — redirects standard error to the same destination as standard output.
  • & — asks the shell to start the command in the background.

Check the log:

tail -f process.log

Press Ctrl+C to stop following the log. This stops tail, not the Python process.

Find the script:

pgrep -af process_data.py

Inspect the result carefully before taking action. Command-line matching can return multiple processes.

Does nohup guarantee that a job survives everything?

No. It is not a service manager. It doesn't automatically restart a crashed process, supervise its health, or guarantee survival through reboots. Shell behavior, terminal handling, resource limits, and application design still matter.

For a temporary task, nohup may be sufficient. For a production application, use an appropriate managed mechanism, such as a systemd service, a container orchestrator, or a job scheduler.

Important: A background job and a detached job are not the same thing. command & backgrounds a job, but doesn't by itself guarantee that it will survive logout.

9. Realistic DevOps case study: a deployment script appears stuck

Scenario: You're connected to an Ubuntu server through SSH. A deployment script is taking longer than expected, and the application hasn't updated.

Your goal is to diagnose the problem without accidentally terminating a critical service.

Step 1 — Find the process

pgrep -af deploy

If you don't find it, inspect your own processes:

ps -u "$USER" -f

Don't assume a process is stuck merely because it has been running for a long time.

Step 2 — Inspect the PID and parent

Suppose you identify a relevant PID of 2450 in the output. Verify that the command and user are what you expect:

ps -p 2450 -o pid,ppid,user,stat,etime,%cpu,%mem,cmd

The PID here is only an example. Use the actual verified PID from your system.

Step 3 — Inspect logs and resource activity

If the deployment writes a log:

tail -n 50 deploy.log

Look for the latest error messages and whether progress has stopped. If appropriate, inspect resource use with:

top

A process consuming no CPU could be waiting for a network response, disk I/O, a lock, or user input. It isn't necessarily broken.

Step 4 — Check whether the process is a shell job

If you launched the script from your current shell:

jobs -l

If it is suspended, fg may bring it back to the foreground so you can inspect or interact with it. If it is an unrelated service process, jobs won't help.

Step 5 — Decide on a safe next action

Use this decision guide:

Deployment seems stuck

Check PID, user, command, state, and logs

Progress exists

Wait or investigate expected processing time.

No progress

Investigate dependencies, locks, input, and errors.

If termination is justified

Use the application's documented shutdown or an approved graceful termination process.

For a managed service, check its status and logs using the appropriate service manager rather than killing a worker blindly.

Step 6 — If the task needs to continue after SSH disconnects

For a suitable, non-production batch script, you might start it with:

nohup python3 process_data.py > process.log 2>&1 &

For production deployments, prefer a supervised service or job runner with logging, status reporting, restart behavior, and clear ownership.

Case study takeaway: Observe first, identify the correct process, understand its state, inspect logs, then take the least disruptive action.

Bonus: practise nohup safely

Create a tiny batch job that prints a timestamp every five seconds:

mkdir -p ~/devops-lab/lesson7
cd ~/devops-lab/lesson7

nohup bash -c 'for i in 1 2 3 4 5; do date; sleep 5; done' > timestamps.log 2>&1 &

Inspect the output:

cat timestamps.log
tail -f timestamps.log

The script ends on its own after five iterations. Use Ctrl+C to stop tail -f when you've seen enough; the logger will finish independently.

Five rules for safe process management

  1. Identify before acting: verify the PID, command, user, and parent process.
  2. Observe before terminating: inspect logs, state, and resource usage.
  3. Prefer graceful shutdown: use SIGTERM or the application's documented shutdown procedure before considering SIGKILL.
  4. Know your shell: jobs, fg, and bg work with jobs managed by the current shell.
  5. Use supervision for production: use service managers or job schedulers for restart policies, monitoring, and reliable lifecycle management.
