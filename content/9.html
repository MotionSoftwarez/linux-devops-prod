Linux networking fundamentals

Beginner-friendly

Hands-on lab

DevOps troubleshooting

In this lesson, you'll learn how a Linux server connects to other machines, how to inspect IP addresses and ports, how DNS translates names into IP addresses, and how to diagnose a website that won't load.

We'll use Ubuntu-oriented commands and a realistic web-server troubleshooting scenario. Most inspection commands are safe to run on a production server; some network tests depend on firewall rules and network policy.

1. How Linux networking works

Imagine that your application runs on a Linux server. A browser wants to access it using a domain name such as app.example.com.

Several things must work together:

Client / browser

Requests a website

DNS lookup

Finds the IP address for the domain

Network route

Packets travel toward the destination

Linux server and port

A service listens for connections, e.g. HTTPS on TCP 443

Application response

The browser receives an HTTP response

If any stage fails, the website may not work. Your job as a DevOps engineer is to find which stage is failing, instead of randomly changing configuration.

Essential networking terms

Term Simple explanation
IP address Network address of a device or interface
Subnet A range of IP addresses that share a network prefix
Gateway Router used to reach networks outside the local subnet
DNS Resolves names such as example.com to IP addresses
Port Identifies a service endpoint on a machine
TCP Transport protocol that establishes a connection
UDP Transport protocol commonly used for DNS and other services
HTTP/HTTPS Web application protocols
Firewall Rules that allow or block network traffic

2. Understand an IP address

An IPv4 address looks like this:

192.168.1.25

An IPv6 address looks like this:

2001:db8::25

IPv4 uses 32-bit addresses; IPv6 uses 128-bit addresses.

A machine can have multiple network interfaces, and each interface can have one or more IP addresses. For example, a cloud VM might have a private address on its network interface and a public address assigned through cloud networking or NAT.

3. Inspect the network with ip

The ip command is the standard modern Linux tool for inspecting and managing network interfaces, addresses, routes, and neighbors.

See network interfaces and IP addresses

ip addr

Short form:

ip a

Example output, simplified:

2: eth0: <BROADCAST,MULTICAST,UP>
    inet 192.168.1.25/24
    inet6 2001:db8::25/64
  • eth0 is an example interface name.
  • inet shows an IPv4 address.
  • inet6 shows an IPv6 address.
  • /24 is the IPv4 network prefix length.
  • UP indicates the interface is administratively enabled.

Interface names may instead be things like ens160, enp0s3, or wlan0.

See a concise address listing

ip -br addr

Check whether an interface is up

ip link show

Inspect routing

ip route

Example:

default via 192.168.1.1 dev eth0
192.168.1.0/24 dev eth0 proto kernel scope link

The default route tells Linux where to send traffic when there isn't a more specific matching route.

Visual: choosing a route

Linux server

192.168.1.25

Destination lookup

Does a specific route match?

Yes

Use the matching route.

No

Use the default route, if one exists.

Test how Linux would route traffic to an example public IP:

ip route get 1.1.1.1

This inspects the local routing decision. It does not prove that the destination is reachable.

Safe practice: Start with ip addr, ip route, and ip link show to inspect. Avoid commands that change interface addresses, routes, or link state on a remote server unless you have authorization and a recovery plan; a mistake can disconnect your SSH session.

4. Test connectivity with ping

ping sends ICMP Echo Requests and checks whether responses return.

ping -c 4 1.1.1.1
  • -c 4 sends four requests, then stops.
  • 1.1.1.1 is an example public DNS resolver address.

You may see output such as:

64 bytes from 1.1.1.1: icmp_seq=1 ttl=57 time=12 ms

This means a response arrived for that probe. The time is the round-trip time for that packet.

How to interpret results

  • Replies arrive: ICMP connectivity to that destination is working.
  • 100% packet loss: Could mean a connectivity problem, but ICMP may also be filtered.
  • Destination unreachable: A local or intermediate system reports that the destination cannot be reached.
  • High latency: Could indicate network congestion, distance, or other delays.

Test a hostname too:

ping -c 4 example.com

This involves name resolution as well as ICMP connectivity. If the hostname test fails but the IP-address test works, investigate DNS first.

Important: A successful ping does not prove a web application is working. A server may block ICMP while serving HTTPS normally, or allow ICMP while its web service is broken.

5. Check web connectivity with curl

curl is one of the most useful DevOps networking tools. It sends requests to URLs and can show response headers, HTTP status codes, and connection errors.

Make a basic request

curl https://example.com

This prints the response body to the terminal.

Show response headers

curl -I https://example.com

This sends a HEAD request. Some servers treat HEAD differently from GET, so a failure here does not always mean a normal GET request would fail.

Show connection and timing details

curl -v --connect-timeout 5 https://example.com/

Verbose output can help distinguish DNS lookup, connection establishment, TLS negotiation, and HTTP response problems.

Print only the HTTP status code

curl -sS -o /dev/null -w '%{http_code}\n' https://example.com/

Common status codes:

Status Meaning
200 Request succeeded
301 / 302 Redirect
400 Bad request
401 / 403 Authentication required or access forbidden
404 Resource not found
500 Server-side application error
502 Gateway received an invalid upstream response
503 Service unavailable
504 Gateway timed out waiting for upstream

A status code of 000 from curl commonly means no HTTP response code was received, such as when the connection or TLS negotiation failed.

Test a local web service

If the app is supposed to be available on the same machine at port 8080:

curl -v --connect-timeout 3 http://127.0.0.1:8080/

This tests the local loopback connection. It doesn't prove the service is reachable from another machine.

Trace a redirect

curl -IL --max-redirs 5 https://example.com/

This requests headers and follows redirects, up to the specified limit.

Safe practice: Use trusted URLs. Avoid sending credentials, session tokens, or private headers in commands that may be saved in shell history. Don't use curl to pipe untrusted internet content directly into a shell.

6. Understand ports and inspect them with ss

An IP address identifies a network endpoint's host/interface; a port identifies a service endpoint within that host.

Examples of common ports:

Port Typical use
22 SSH
53 DNS
80 HTTP
443 HTTPS
3306 MySQL
5432 PostgreSQL
8080 Common alternative web/application port

These are conventions, not guarantees: services can be configured to use different ports.

See listening TCP and UDP sockets

ss -lnt
ss -lun
  • -l — listening sockets.
  • -n — show numeric addresses and ports.
  • -t — TCP.
  • -u — UDP.

For process details, use:

sudo ss -lntup

This can show the processes associated with listening sockets, where permissions and system support allow.

Example:

State   Local Address:Port
LISTEN  0.0.0.0:80
LISTEN  0.0.0.0:22
LISTEN  127.0.0.1:8080

Interpretation:

  • 0.0.0.0:80 means a service is listening on all IPv4 addresses on port 80.
  • 127.0.0.1:8080 means it is listening only on the IPv4 loopback address.
  • A service listening only on loopback is not directly reachable through the server's external interface.

IPv6 listeners, firewall rules, cloud security groups, NAT, and routing can further affect reachability.

Visual: where a connection can fail

Client

Connects to server IP and port 443

Network / firewall

Route and access rules permit the traffic?

Server socket

Is a service listening on the target address and port?

Application

Does it handle the request successfully?

A closed port, a filtered connection, and a service returning an HTTP error are different problems. The diagnostic command should help distinguish them.

7. DNS: translate names into IP addresses

DNS, the Domain Name System, maps domain names to records such as IP addresses.

For example:

app.example.com  →  203.0.113.10

The IP shown here belongs to a documentation-only address range and is just an example.

Use getent

getent hosts example.com

This uses the system's configured name-service lookup path, which may include DNS, local files, or other configured sources.

Use resolvectl on systemd-resolved systems

resolvectl status
resolvectl query example.com

These commands are useful when systemd-resolved manages name resolution. The command may not be available or relevant on every Linux distribution.

Use dig or nslookup

If installed:

dig example.com
dig example.com A
dig example.com AAAA
nslookup example.com
  • A records return IPv4 addresses.
  • AAAA records return IPv6 addresses.
  • dig displays DNS query details, including response status and answer records.

To query a particular DNS resolver:

dig @1.1.1.1 example.com

This tests that resolver specifically; it does not necessarily reflect the DNS resolver your server normally uses.

Check local name-resolution configuration

cat /etc/resolv.conf
cat /etc/hosts

/etc/resolv.conf may be managed automatically, so avoid editing it directly without understanding how the system configures DNS. /etc/hosts can contain local static hostname mappings.

DNS troubleshooting flow

Hostname fails

Check resolution

getent hosts example.com

No result

Check resolver configuration and DNS reachability.

Address returned

Test routing and the service at that address.

A DNS lookup that succeeds doesn't prove that the returned address is correct for your environment or that the service is reachable.

8. Check the hostname and local network configuration

The hostname command displays or manages the system's hostname.

hostname
hostname -f
hostnamectl
  • hostname — shows the current hostname.
  • hostname -f — attempts to show the fully qualified domain name, depending on system configuration and name resolution.
  • hostnamectl — displays system hostname information on systems using systemd.

A machine's hostname is not necessarily its public DNS name.

To inspect neighbor information for devices on the local network:

ip neigh

This displays the local neighbor table, often using ARP for IPv4 and Neighbor Discovery for IPv6. An entry may be missing or stale if the host has not recently communicated with that neighbor.

Quick network inspection bundle

Run these commands when you first connect to a Linux server:

hostname
ip -br addr
ip route
ip neigh
ss -lnt

These commands provide a quick overview of the hostname, addresses, routes, neighbors, and listening TCP ports.

9. Realistic DevOps case study: website returns “connection refused”

Scenario: Your application is deployed on an Ubuntu server. A teammate reports that http://server-address:8080 isn't opening.

You need to find out whether the problem is DNS, routing, firewall policy, the listening socket, or the application itself.

Step 1 — Confirm the server identity and address

On the server:

hostname
ip -br addr
ip route

Verify you're logged into the correct server and that its network interface has the expected address.

Step 2 — Check whether the application is listening

sudo ss -lntp

Look for port 8080.

Possible findings:

  • Nothing is listening on port 8080: check the application process and its startup logs.
  • The app listens on 127.0.0.1:8080: it accepts local connections only.
  • The app listens on 0.0.0.0:8080: it accepts IPv4 connections on all local IPv4 interfaces, subject to firewall and network controls.

Step 3 — Test locally

curl -v --connect-timeout 3 http://127.0.0.1:8080/

If this fails, investigate the service itself before assuming the problem is external networking.

If it succeeds, test the server's intended interface address locally, where appropriate:

curl -v --connect-timeout 3 http://SERVER_PRIVATE_IP:8080/

Replace SERVER_PRIVATE_IP with the actual private address. A difference between the two results can reveal a binding or local network configuration issue.

Step 4 — Test from the client

From the client machine:

getent hosts app.example.com
curl -v --connect-timeout 5 http://app.example.com:8080/

If the application is accessed by IP rather than domain, test that IP directly too.

Step 5 — Interpret the symptoms

Symptom What to investigate
DNS name doesn't resolve Resolver settings, DNS records, name-service configuration
Connection refused No listener on that address/port, or an active reject rule
Connection times out Firewall drops, routing, security groups, or an unresponsive destination
Local curl works, remote curl fails Listening address, host firewall, network ACLs, routing, or cloud firewall
HTTP 502 Reverse proxy or gateway cannot get a valid upstream response
HTTP 503 Application unavailable, overloaded, or deliberately returning unavailable
HTTP 404 Server responds, but the requested route or resource wasn't found
TLS certificate error Certificate validity, hostname mismatch, or certificate-chain configuration

These are diagnostic clues, not definitive conclusions. For example, a timeout can also occur when a host is down, and a refusal can originate from an intermediate network device.

Step 6 — Check the service logs

For an application managed by systemd, use its real service name:

sudo systemctl status nginx
sudo journalctl -u nginx --since "15 minutes ago"

These examples inspect Nginx. If your application uses another service name, substitute that name.

Step 7 — Make a controlled fix

If the application is configured to listen only on loopback but must accept connections from a reverse proxy or another network interface, adjust its configuration according to the intended architecture. Validate the configuration before applying it.

If a firewall or cloud security group is blocking the traffic, request or implement the narrowest approved rule needed for the intended clients.

Avoid blindly opening all ports or binding an application to every interface. A direct application port might be intended to remain private behind Nginx or another reverse proxy.

Case study takeaway: Test from the server outward, then from the client inward. Each test narrows the failure point.
