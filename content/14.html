Learn how to securely connect to a remote Linux server, authenticate with SSH keys, transfer files, troubleshoot connection failures, and avoid locking yourself out of a production server.

1. What is SSH?

SSH (Secure Shell) is a protocol that lets you securely access and manage another computer over a network. The connection is encrypted, so credentials and commands aren't sent as ordinary readable text.

For example, suppose your Ubuntu server runs a Python application or a Perl-based dataset validation tool. Instead of sitting in front of that server, you can connect from your laptop and inspect logs, restart services, and deploy files remotely.

The basic architecture

SSH client — your computer

Runs the ssh command

Encrypted SSH connection

Usually TCP port 22

SSH server — remote Ubuntu

Usually the sshd service

Two parts are involved:

  • Client: the computer initiating the connection.
  • Server: the remote computer running an SSH server, commonly OpenSSH.

SSH is useful for remote terminals, secure file transfers, deployment, server maintenance, and automation.

2. Install and check SSH on Ubuntu

SSH client and SSH server are separate components. Your laptop may already have the client installed even if the SSH server is not installed.

On the client computer

Check whether SSH is available:

ssh -V

If Ubuntu reports that the command is missing, install the client:

sudo apt update
sudo apt install openssh-client

On the remote Ubuntu server

Install the server package if needed:

sudo apt update
sudo apt install openssh-server

Check its status:

sudo systemctl status ssh

Start it now and enable it at boot:

sudo systemctl enable --now ssh

Check whether it is listening:

sudo ss -lntp | grep ':22'

Note: SSH can be configured to use a different port. A running service also doesn't guarantee that remote connections are allowed through the firewall or network.

3. Make your first SSH connection

The basic syntax is:

ssh username@server_ip

Example with illustrative values:

ssh deploy@192.0.2.10

Here:

  • deploy is the account on the remote server.
  • 192.0.2.10 is a documentation-only example IP address.
  • You may be asked to verify the server's host key on the first connection.

If the server is configured for password authentication, SSH may ask for the remote account's password. If key authentication is configured, it may use your private key instead.

After connecting, try:

whoami
hostname
pwd

These commands help confirm which account and machine you're actually using.

To disconnect:

exit

Connect on a non-default port

If the server uses port 2222:

ssh -p 2222 deploy@192.0.2.10

Remember: -p specifies the SSH server port, not a port for your application.

4. Understand SSH host keys

The first time you connect to a server, SSH may display a message asking whether you trust its host key.

This key helps identify the server and detect unexpected changes to its identity.

Do not automatically accept every host key. Verify the server fingerprint through a trusted channel, such as your administrator or cloud console.

If SSH later reports that the host identification has changed, stop and investigate. The server may have been rebuilt, its keys may have been rotated, or there could be a security issue. Do not blindly delete the warning to make the connection work.

5. Public-key authentication: the safer approach

Passwords can be guessed, reused, or exposed. SSH keys offer a strong alternative and are commonly used for DevOps administration.

An SSH key pair contains two related keys:

  • Private key: stays on your client computer. Keep it secret.
  • Public key: can be installed on the remote server.

How authentication works

1. Client creates a key pair

Private key: id_ed25519 · Public key: id_ed25519.pub

2. Public key is installed on the server

Typically in the remote user's ~/.ssh/authorized_keys file.

3. Client proves possession of the private key

The server verifies the proof using the matching public key.

Access granted if the checks pass

The private key is not supposed to be copied to the server. Only the public key is installed there.

Step 1 — Generate an SSH key pair

On your client computer:

ssh-keygen -t ed25519 -C "devops-laptop"

Follow the prompts. The default key paths are usually:

~/.ssh/id_ed25519
~/.ssh/id_ed25519.pub

Set a passphrase when practical. It protects the private key if someone obtains a copy of the file. An SSH agent can help you avoid entering the passphrase repeatedly.

If the default key already exists, don't overwrite it without checking whether you still need it.

Check the files:

ls -la ~/.ssh

Step 2 — Copy the public key to the server

If password-based SSH access is currently permitted and you have authorization:

ssh-copy-id deploy@192.0.2.10

For a server using port 2222:

ssh-copy-id -p 2222 deploy@192.0.2.10

This installs the public key into the remote user's authorized keys, usually ~/.ssh/authorized_keys.

If ssh-copy-id is unavailable, a system administrator can install the public key through an approved access method.

Step 3 — Test key-based login

ssh deploy@192.0.2.10

To specify a particular private key:

ssh -i ~/.ssh/id_ed25519 deploy@192.0.2.10

You can test key authentication explicitly:

ssh -o PreferredAuthentications=publickey \
    -o PasswordAuthentication=no \
    deploy@192.0.2.10

This test may fail if the server or account isn't configured for key-based access. Don't disable other authentication methods on a production server until you've verified your intended access path.

6. SSH directory and file permissions

OpenSSH may reject keys if the user's home directory, SSH directory, or key files have unsafe ownership or permissions.

Typical permissions for a personal key setup are:

Path Typical permission Purpose
~/.ssh 700 Only the owner can access the directory
~/.ssh/id_ed25519 600 Private key
~/.ssh/id_ed25519.pub 644 Public key
~/.ssh/authorized_keys 600 Public keys permitted to log in

Set permissions on your own client:

chmod 700 ~/.ssh
chmod 600 ~/.ssh/id_ed25519
chmod 644 ~/.ssh/id_ed25519.pub

On the remote server, as the relevant user or administrator:

chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys

Check ownership as well:

ls -ld ~ ~/.ssh
ls -l ~/.ssh

The SSH directory and authorized-keys file should normally belong to the intended account. Don't use chmod -R or change ownership across an entire home directory without understanding the effects.

Important: Never share your private key in a ticket, email, chat, Git repository, or public server. If a private key is exposed, treat it as compromised and replace it.

7. Transfer files with scp

scp copies files securely over SSH. It is useful for transferring deployment artifacts, configuration files, reports, and logs.

Copy a file from your laptop to the server

scp ./app.conf deploy@192.0.2.10:/home/deploy/

Download a server log to your laptop

scp deploy@192.0.2.10:/var/log/myapp/app.log ./

You may need appropriate read permissions to download a server file.

Copy an entire directory

scp -r ./myapp deploy@192.0.2.10:/home/deploy/

Use a custom SSH port

scp -P 2222 ./app.conf deploy@192.0.2.10:/home/deploy/

Notice the difference: SSH uses lowercase -p for a port; SCP uses uppercase -P.

Visual example: upload a deployment file

Client

./app.conf

Remote server

/home/deploy/app.conf

Copy upload command

For large directory synchronization or repeat deployments, rsync -e ssh is often more efficient because it can transfer only changed data. For interactive file browsing, consider sftp.

Be careful when transferring configuration files: a successful copy does not mean the application is configured correctly or that the file should be installed into a privileged directory.

8. Save connection settings in SSH config

Typing long commands every time gets tedious. SSH supports a client configuration file at ~/.ssh/config.

Create or edit it:

nano ~/.ssh/config

Add a host entry, replacing the example address and username with the real values:

Host staging
    HostName 192.0.2.10
    User deploy
    Port 2222
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes

Set appropriate permissions:

chmod 600 ~/.ssh/config

Now you can connect using the short alias:

ssh staging

And copy files:

scp ./app.conf staging:/home/deploy/

This file is on your client, not the remote server. Avoid putting passwords or private-key contents in it.

9. Troubleshoot SSH like a DevOps engineer

When SSH fails, first identify the exact error. Different errors usually point to different layers of the connection.

Error Common causes First checks
Connection timed out Routing, firewall, security group, unreachable host IP, route, network/firewall rules
Connection refused Server reachable but port not accepting connections SSH service and listening port
Permission denied (publickey) Wrong user/key, missing public key, permissions Username, key selection, authorized_keys
Host key verification failed Host identity mismatch or stale entry Verify fingerprint before changing trust
Could not resolve hostname Typo or DNS problem Hostname, getent hosts
REMOTE HOST IDENTIFICATION HAS CHANGED Server rebuilt, host key rotated, or possible attack Verify through a trusted channel

Useful diagnostic commands

Show detailed connection information:

ssh -v deploy@192.0.2.10

Use -vv or -vvv for more detail if necessary. Review output before sharing it; logs can contain usernames, hostnames, paths, and other sensitive information.

Check the route to a server:

ip route
ip route get 192.0.2.10

Check the SSH service on the remote Ubuntu server:

sudo systemctl status ssh
sudo journalctl -u ssh -n 50 --no-pager
sudo ss -lntp

Check the SSH server configuration syntax:

sudo sshd -t

If this command returns no output, the configuration syntax check generally passed. It does not prove that every access rule or network path will work.

Check the DNS result:

getent hosts staging.example.com

If a custom port is configured, make sure the client, SSH server, firewall, and any cloud security rules agree on that port.

A safe troubleshooting sequence

1. Confirm the destination

Check the hostname/IP, username, port, and network route.

2. Confirm connectivity

Look for timeouts, refused connections, or DNS failures.

3. Check authentication

Verify the user, selected key, public key, ownership, and permissions.

4. Inspect server logs

Use the journal and configuration checks to identify the actual cause.

10. Configure the SSH server safely

The server's main configuration file is usually:

/etc/ssh/sshd_config

Some Ubuntu installations also use additional configuration files under:

/etc/ssh/sshd_config.d/

Inspect the active configuration and any included files before changing settings.

For example, you might eventually configure key-based authentication or restrict SSH access to approved users. However, don't blindly copy hardening settings from a tutorial into a production server. The effective configuration can depend on included files, defaults, and Match rules.

Safe procedure before changing SSH settings

  1. Keep your current SSH session open.
  2. Make a backup of the configuration file you plan to edit.
  3. Make one change at a time.
  4. Validate syntax with sudo sshd -t.
  5. If validation succeeds, reload the service if appropriate:
sudo systemctl reload ssh
  1. Open a second terminal and verify that a new connection works.
  2. Only then close the original session.

If reload isn't supported in your setup, investigate the appropriate service action before proceeding. Maintain console or out-of-band recovery access for important servers.

Don't lock yourself out

Avoid disabling password authentication or root login until you have confirmed that the intended account can successfully authenticate using a key and has the required administrative access.

Other safety rules:

  • Don't expose port 22 to the entire internet unless your security design calls for it.
  • Prefer approved source-IP restrictions, VPN access, or a bastion host where appropriate.
  • Use individual accounts and least-privilege access rather than sharing one administrator account.
  • Keep private keys protected and rotate them when needed.
  • Don't use chmod 777 to fix SSH permission problems.

11. Real-world DevOps case study: deployment server unreachable

Imagine a Python web application is running on an Ubuntu staging server. A deployment engineer suddenly receives:

ssh: connect to host 192.0.2.10 port 22: Connection refused

The application team cannot access the server using SSH.

Investigation

Step 1 — Interpret the error. A refusal commonly means the destination is reachable but nothing is accepting connections at that address and port, or a network device is actively rejecting the connection. It does not automatically mean the password or SSH key is wrong.

Step 2 — Use the approved server console. If SSH is unavailable, access the server through its cloud console, hypervisor console, or another authorized recovery route.

Step 3 — Check the service.

sudo systemctl status ssh
sudo journalctl -u ssh -n 50 --no-pager

Suppose the service is inactive after a maintenance change.

Step 4 — Check the configuration before starting it.

sudo sshd -t

If syntax is valid and the service is meant to be running, start it:

sudo systemctl start ssh

Step 5 — Confirm it is listening.

sudo ss -lntp | grep ':22'

Step 6 — Test a new connection from the client.

ssh -v deploy@192.0.2.10

Step 7 — Verify the outcome. Confirm the expected account can log in and inspect the service logs for any remaining errors.

What if the real cause is different?

  • If the service is running but no socket is listening on port 22, inspect the configured port and listen addresses.
  • If the connection times out, investigate network paths, firewalls, cloud security groups, and routing.
  • If the error is Permission denied (publickey), investigate authentication instead of restarting the service.
  • If SSH reports a host key change, verify the server identity before updating the client's trust record.

DevOps lesson: Diagnose the layer that failed. Restarting services, changing permissions, or disabling security controls without evidence can make the incident worse.

Challenge B — Diagnose a key problem

Before changing server security settings, inspect:

  • The username used in the command.
  • Which private key the client is offering (ssh -v).
