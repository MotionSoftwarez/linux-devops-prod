In this lesson, you'll learn how to identify why a Linux server is slow, whether CPU or memory is exhausted, whether storage is causing delays, and which process deserves investigation.

1. What is system monitoring?

System monitoring means observing a computer's health and resource usage so that problems can be detected before they cause an outage.

Imagine a Python web application or a Perl-based journal validation tool running on an Ubuntu server. A user reports that the application is slow. Restarting it immediately might hide the symptoms without fixing the cause.

A DevOps engineer checks the evidence first.

The four major resource areas

CPU

Is the processor busy executing work?

Tools: top, mpstat

Memory

Is RAM under pressure or is swapping occurring?

Tools: free, vmstat

Disk I/O

Are storage operations slowing down?

Tools: iostat, vmstat

Processes and load

What is running, waiting, or consuming resources?

Tools: ps, uptime, top

A useful principle: measure first, identify the bottleneck, then change one thing at a time.

2. Start with a quick health check

Run these read-only commands on your Ubuntu server:

uptime
free -h
df -h
ps aux --sort=-%cpu | head -n 10
ps aux --sort=-%mem | head -n 10

What each command tells you:

Command What it checks
uptime Uptime, logged-in users, load average
free -h Memory and swap usage
df -h Filesystem capacity
ps aux --sort=-%cpu Processes using the most CPU
ps aux --sort=-%mem Processes using the most RAM

These checks provide a first snapshot, not a complete diagnosis. For example, a filesystem may have free space but be slow because its storage device is overloaded.

3. CPU monitoring

The CPU executes instructions for your programs. If too much work competes for CPU time, requests and background jobs may take longer.

Check CPU usage with top

top

Useful fields include:

  • PID — process ID.
  • USER — process owner.
  • %CPU — CPU usage reported for that process.
  • %MEM — memory usage.
  • TIME+ — accumulated CPU time.
  • COMMAND — process command name.

Press q to quit top.

You can also run a short snapshot:

top -b -n 1 | head -n 20

Here, -b selects batch mode and -n 1 takes one iteration.

Find CPU-heavy processes

ps -eo pid,ppid,user,%cpu,%mem,stat,comm --sort=-%cpu | head -n 15

Example output might show a Python worker using a large share of CPU. That is a clue to investigate—not automatic proof that the worker is broken.

CPU percentages can exceed 100% for a process using multiple CPU cores, depending on the tool's reporting convention.

Install htop for an easier view

If permitted on your Ubuntu server:

sudo apt update
sudo apt install htop
htop

htop provides a visual process list, CPU meters, memory meters, sorting, and interactive navigation. Press q to exit.

Understand CPU states

In top, the CPU summary commonly includes:

  • us — user-space work.
  • sy — kernel/system work.
  • id — idle CPU time.
  • wa — time waiting for I/O.
  • st — CPU time taken by the hypervisor from a virtual machine.

A high wa value can suggest an I/O bottleneck rather than a CPU computation bottleneck. These percentages are snapshots and should be interpreted alongside other evidence.

4. Load average: is the server overloaded?

The load average appears in uptime and top.

Example:

20:45:00 up 12 days,  3:10,  2 users, load average: 2.10, 1.80, 1.25

The three load values represent approximate system load averages over the past 1, 5, and 15 minutes.

Unlike CPU utilization, load average reflects tasks that are runnable and tasks in certain uninterruptible waiting states, often associated with I/O.

How to interpret it

A load average of 4 does not automatically mean the server is overloaded. You need to compare it with the number of logical CPUs and examine what tasks are waiting.

For example:

An illustrative 4-vCPU server

Load average: 1

Relatively light

Load average: 4

Around CPU capacity

Load average: 8

Potential contention

These are illustrative comparisons, not a universal health scale. A load above the CPU count can be caused by runnable work, I/O waits, or both.

Check the logical CPU count:

nproc

Then check load:

uptime

A load average consistently higher than the CPU count is a reason to investigate, not a reason to kill processes immediately. Look at CPU use, process states, and I/O waits to understand why.

5. Memory monitoring with free

RAM holds the data and code programs need while they run.

Check memory:

free -h

Example:

               total   used   free  shared  buff/cache  available
Mem:             8Gi   5.2Gi  500Mi  200Mi       2.3Gi      2.1Gi
Swap:            2Gi   100Mi  1.9Gi

The figures above are illustrative.

The most important field for an initial check is often available. Linux uses otherwise-unused memory for caches, so low free memory by itself does not mean RAM is exhausted.

  • total: total recognized RAM.
  • used: memory currently in use according to free's accounting.
  • free: memory not currently used.
  • buff/cache: buffers and caches.
  • available: estimated memory that can be made available to applications without swapping.

What is swap?

Swap is disk space used to hold memory pages that are not currently kept in RAM. It can help a system cope with memory pressure, but heavy swapping can make applications much slower than working in RAM.

Check swap configuration and usage:

swapon --show
free -h

Don't assume that some swap usage means a problem. Look for sustained swapping, low available memory, application latency, and related kernel messages.

Identify memory-heavy processes

ps -eo pid,ppid,user,%mem,rss,comm --sort=-%mem | head -n 15

RSS is resident memory, usually shown in KiB. Summing process RSS values does not give an exact system-wide memory total because shared memory can be counted more than once.

If an application steadily grows in memory use over time, investigate whether it has a memory leak, a growing cache, too many workers, or unexpectedly large jobs.

6. Use vmstat to observe system activity

vmstat provides a compact view of processes, memory, swap, I/O, and CPU.

Install it if necessary:

sudo apt install procps

Run:

vmstat 1 5

This reports five samples at one-second intervals. The first report is often an average since boot, so pay particular attention to the subsequent samples.

Key columns include:

Column Meaning
r Runnable processes waiting for CPU time
b Processes blocked, often waiting for I/O
si / so Swap-in / swap-out activity
bi / bo Blocks received from / sent to block devices
us / sy CPU time in user / system mode
id Idle CPU time
wa CPU time waiting for I/O

A sustained rise in r can indicate CPU contention. Sustained si/so alongside low available memory can indicate memory pressure. A high b or wa can point toward I/O waits, but confirm with more detailed disk and process evidence.

7. Monitor disk I/O with iostat

Disk capacity and disk performance are different things. A filesystem can have plenty of free space while a storage device is responding slowly.

Install iostat on Ubuntu through the sysstat package:

sudo apt update
sudo apt install sysstat

Then run:

iostat -xz 1 5

This displays extended device statistics at one-second intervals. The first report can represent averages since boot; later reports are usually more useful for diagnosing a current slowdown.

Important fields commonly include:

  • r/s, w/s: read and write operations per second.
  • rMB/s, wMB/s or equivalent throughput columns: data transferred per second, depending on version.
  • await: average I/O request time, typically in milliseconds.
  • aqu-sz: average queue length.
  • %util: proportion of time the device was busy handling I/O.

Interpretation caution: High %util can indicate a busy device, but it is not a universal saturation threshold for every SSD, RAID array, or cloud volume. Compare it with latency, throughput, queueing, and the storage platform's expected limits.

Storage diagnosis workflow

Symptom: application requests are slow

Check vmstat 1 5 for sustained I/O waits or blocked processes.

Check iostat -xz 1 5 for latency, queueing, throughput, and device activity.

Compare results with application logs, disk capacity, and storage-service metrics before deciding on a fix.

If iostat isn't available, vmstat, df -h, du, and process inspection can still provide useful clues. Don't assume that disk I/O is the cause just because an application reads files.

8. Find and inspect resource-heavy processes

Use ps for a process snapshot:

ps -ef

Sort by CPU:

ps aux --sort=-%cpu | head -n 10

Sort by memory:

ps aux --sort=-%mem | head -n 10

Inspect a particular process:

ps -p 1234 -o pid,ppid,user,%cpu,%mem,stat,etime,cmd

Replace 1234 with the actual PID.

You can inspect the process tree too:

pstree -p

If pstree is missing, install the psmisc package or use ps -ef instead.

What should you do with a high-CPU process?

Don't immediately run kill -9.

First:

  1. Identify the command, owner, parent process, and purpose.
  2. Check whether it is an expected batch job or service.
  3. Review relevant application and service logs.
  4. Check whether usage is sustained or a brief spike.
  5. Follow the application's normal stop, restart, or incident procedure.

For a systemd-managed service, prefer the service manager over manually killing one of its processes.

sudo systemctl status myapp
sudo journalctl -u myapp --since "15 minutes ago"

10. Real-world DevOps case study: a slow validation server

Imagine your Ubuntu server runs a large Perl dataset validation tool. Users report that packages that previously finished in a few minutes now take 25 minutes. The application hasn't crashed, but the queue is growing.

Step 1 — Establish the baseline

uptime
nproc
free -h
df -h

Suppose the server has four logical CPUs and a load average of 9.5, 8.8, 7.9. This suggests sustained load above CPU count, but does not establish the cause.

Step 2 — Inspect CPU consumers

ps -eo pid,ppid,user,%cpu,%mem,stat,etime,comm --sort=-%cpu | head -n 15

Suppose a Perl validation process uses most of one CPU. That might be normal for a CPU-heavy job. Compare it with historical runtimes and check whether several jobs are competing for resources.

Step 3 — Check memory and swapping

free -h
vmstat 1 5

Suppose available memory is healthy and si/so remain near zero across subsequent samples. That makes sustained swapping a less likely explanation, though it does not rule out every memory-related problem.

Step 4 — Check storage

iostat -xz 1 5
df -h

Suppose the storage device has moderate latency and no clear queue buildup, while CPU remains busy. The evidence points more toward CPU work or excessive concurrent validation jobs than storage saturation.

Step 5 — Check the application

Review recent logs and job metrics:

sudo journalctl -u validator --since "30 minutes ago"

If the tool logs to its own file instead, inspect that configured application log.

Suppose the slowdown began after a configuration change increased the number of concurrent validation workers. Each worker performs CPU-intensive XML and rule checks.

Step 6 — Apply a measured fix

  • Compare worker count and processing throughput with the previous configuration.
  • Reduce concurrency to an approved value if evidence supports it.
  • Avoid killing active validation jobs without checking their impact on output files and queue state.
  • Measure processing time, queue depth, CPU utilization, and error rates after the change.

Step 7 — Verify recovery

Repeat the same monitoring commands and compare against the baseline. Confirm that package processing times improve and no jobs are lost or left partially written.

Lesson: Resource monitoring helps connect a user-facing symptom to evidence. It is much more reliable than assuming every slow server needs more RAM or a reboot.

Reset lab checklist

Challenge: identify the bottleneck

Record the output of uptime, nproc, free -h, vmstat 1 5, and ps aux --sort=-%cpu | head -n 10.

Then answer these questions in your notes:

  1. Is load average high relative to the CPU count?
  2. Is memory available, or is there evidence of memory pressure?
  3. Are processes competing for CPU time?
  4. Is there evidence of storage I/O waiting?
  5. What additional evidence would you need before changing anything?

A single snapshot is not enough to establish a trend. Repeat measurements when appropriate and compare with a known healthy baseline.
