Disk management and storage troubleshooting on Ubuntu

Learn to inspect disks, understand Linux filesystems and mount points, diagnose disk-space and inode exhaustion, and troubleshoot storage problems safely on Ubuntu servers.

1. Understand Linux storage

Imagine an Ubuntu server hosting a Python web application. The application suddenly reports:

OSError: [Errno 28] No space left on device

This error doesn't always mean the physical disk is completely full. Possible causes include:

  • The filesystem has run out of available space.
  • The filesystem has run out of inodes.
  • The application is writing to a different, full mount point.
  • A deleted file is still being held open by a running process.

The first step is to investigate rather than delete files blindly.

The Linux storage hierarchy

Physical or virtual disk

Example: /dev/sda or /dev/vda

Partitions or logical volumes

Example: /dev/sda1, /dev/mapper/ubuntu--vg-root

Filesystem

Example: ext4 or XFS; some setups use Btrfs

Mount point

Example: /, /var, /home, /mnt/data

Think of it like a building:

  • Disk: the entire building.
  • Partition or logical volume: a separate area within the building.
  • Filesystem: the system that organizes and tracks stored items.
  • Mount point: the location where Linux makes that filesystem accessible.

Not every server uses partitions directly. Cloud servers often use virtual disks, and Logical Volume Manager (LVM) can place filesystems on logical volumes instead of directly on partitions.

2. Inspect disks with lsblk

lsblk lists block devices such as disks, partitions, and logical volumes.

Start with:

lsblk

For more useful information:

lsblk -f

To include filesystem type, UUID, size, and mount point in a more explicit layout:

lsblk -o NAME,SIZE,TYPE,FSTYPE,UUID,MOUNTPOINTS

Example output (illustrative):

NAME        SIZE TYPE FSTYPE UUID        MOUNTPOINTS
sda          80G disk
├─sda1        1G part ext4   abc123...   /boot
└─sda2       79G part
  └─vg-root  40G lvm  ext4   def456...   /
sdb         100G disk
└─sdb1      100G part xfs    ghi789...   /mnt/data

This example shows a disk containing a boot partition and an LVM-backed root filesystem, plus a separate disk mounted at /mnt/data. Your actual device names and layout will differ.

3. Check filesystem capacity with df

The df command reports how much space is used and available on mounted filesystems.

# Human-readable sizes
df -h

# Include filesystem types
df -hT

# Check a specific path
df -h /var/log

# Check inode usage
df -i

Example:

Filesystem      Size  Used Avail Use% Mounted on
/dev/mapper/vg-root
                 40G   38G  2.0G  95% /

Here, the root filesystem is 95% used and has approximately 2 GB available. That may be a warning sign, particularly on a busy application server, but the appropriate threshold depends on workload and growth rate.

Read the output correctly

Column Meaning
Filesystem The mounted storage device or filesystem
Size Reported filesystem capacity
Used Space counted as used
Avail Space available to ordinary users, subject to filesystem rules
Use% Percentage used
Mounted on Directory where the filesystem is accessible

A common mistake is to check only df -h /. If /var or /mnt/data is a separate filesystem, it can fill up while / still has plenty of free space.

For a specific application directory:

df -h /opt/myapp
df -h /var/log
df -h /tmp

These commands help identify the filesystem that actually backs each path.

4. Find large directories with du

df tells you about a filesystem. du helps you find which directories and files are consuming space.

# Total size of a directory
du -sh /var/log

# Sizes of immediate subdirectories
sudo du -xhd1 /var/log 2>/dev/null | sort -h

# Check a project directory
du -sh /opt/myapp

Explanation of common options:

  • -s — summarize rather than list every item.
  • -h — display readable units such as MB and GB.
  • -d1 — limit the summary to one directory level on Ubuntu's GNU du.
  • -x — stay on the same filesystem.
  • sort -h — sort sizes in human-readable order.

To find the largest files in a directory, one option is:

sudo find /var/log -xdev -type f -printf '%s %p\n' \
  2>/dev/null | sort -n | tail -n 20

This lists up to 20 of the largest files by byte size, with the largest near the bottom. The byte counts are not human-readable, but they are useful for sorting accurately.

Why can df and du disagree?

Suppose df -h /var reports that the filesystem is nearly full, but du -sh /var/log seems to account for very little usage.

Possible explanations include:

  1. Large files elsewhere on that filesystem.
  2. Files hidden beneath a mount point.
  3. Deleted files still open by running processes.
  4. Filesystem metadata, reserved space, or accounting differences.
  5. Files on a different mount than the one you intended to inspect.

To investigate deleted-but-open files, if the tool is installed:

sudo lsof +L1

Look for large files with a link count of zero. A process may still occupy disk space through an open file descriptor even after the filename has been removed. The space is normally released when the process closes that descriptor. Prefer an application-supported log reopen or restart procedure instead of killing processes blindly.

5. Filesystems: ext4, XFS, and others

A filesystem organizes files, directories, metadata, and free-space tracking on a storage device.

Common types include:

ext4 Demystified: From On-Disk Layout to Hands-On Inspection | by DevOpsIsRil | Medium

ext4

A widely used Linux filesystem and a common choice for Ubuntu root and data volumes. It supports file permissions, directories, journaling, and inode-based file tracking.

XFS for Scalable File Storage | simplyblock

XFS

A high-performance journaling filesystem used in many server environments. Its capacity and inode usage can be inspected with standard tools such as df.

Btrfs File System: Definition, Features, Pros & Cons

Btrfs

A copy-on-write filesystem with features such as snapshots and checksums. Snapshot and subvolume usage can make space accounting more nuanced.

Discover filesystem types and identifiers:

lsblk -f
sudo blkid

blkid reads block-device metadata such as filesystem type and UUID. Some device details may require elevated permissions.

What is a UUID?

A UUID is an identifier associated with a filesystem or block-device structure. It can be used in mount configuration so a system doesn't depend solely on device names such as /dev/sda1, which may vary across environments.

Example:

UUID=1234abcd-...   /mnt/data   ext4   defaults   0  2

This is an illustrative /etc/fstab entry, not a value to copy onto a real server.

Never assume the filesystem type or UUID. Read them from your own system before configuring a mount.

6. Mount points and findmnt

A mount point is a directory through which a filesystem becomes accessible.

Examples:

  • / — root filesystem.
  • /boot — often a separate boot filesystem.
  • /home — users' home directories.
  • /var — frequently contains logs and variable application data.
  • /mnt/data — a common manually configured data mount point.
  • /media — often used for removable media.

Inspect the mount tree:

findmnt
findmnt /
findmnt /var/log
findmnt /mnt/data

If a path is not a separate mount point, findmnt may show the parent filesystem that contains it. This is useful for identifying which filesystem backs a particular directory.

Mounting a filesystem

A normal mount command has the form:

sudo mount DEVICE DIRECTORY

For example, on a test machine, after confirming the device and filesystem and creating the mount directory:

sudo mkdir -p /mnt/data
sudo mount /dev/CONFIRMED_DEVICE /mnt/data

/dev/CONFIRMED_DEVICE is a placeholder, not a literal device name. Do not run this example unchanged.

Mounting an existing filesystem at the wrong location can hide the directory's previous contents while the mount is active. Formatting a device can destroy data. Always identify the device and existing data before making storage changes.

To unmount a filesystem:

sudo umount /mnt/data

Unmounting can fail if processes are using the filesystem. Identify the users and stop or redirect them appropriately instead of forcing an unmount as the first response.

7. Configure persistent mounts with /etc/fstab

The file /etc/fstab describes filesystems that should be mounted according to system configuration, often automatically during boot.

Inspect it without editing:

cat /etc/fstab

A typical entry has six fields:

UUID=your-filesystem-uuid  /mnt/data  ext4  defaults  0  2
Field Example Purpose
1 UUID=... Identifies the device or filesystem
2 /mnt/data Mount point
3 ext4 Filesystem type
4 defaults Mount options
5 0 Legacy dump setting
6 2 Filesystem-check ordering where applicable

The values depend on the actual filesystem and server setup.

Safe workflow for editing /etc/fstab

A mistake in this file can prevent a filesystem from mounting and may complicate boot or recovery.

  1. Identify the device with lsblk -f and blkid.
  2. Verify the intended mount point and filesystem type.
  3. Back up the existing configuration.
  4. Edit carefully, preserving all existing entries.
  5. Test the configuration before rebooting.
  6. Check the mount result and relevant logs.

Example of a backup:

sudo cp -a /etc/fstab /etc/fstab.bak

After editing, on a systemd-based Ubuntu server:

sudo findmnt --verify --verbose

This checks the mount-table configuration, but it does not guarantee that every device is available or that a mount will succeed during boot.

If the configuration is appropriate for the current system and the device is available, you can test mounting configured filesystems:

sudo mount -a

Caution: mount -a may attempt to mount every applicable entry that is not already mounted. Review the configuration first and be especially careful on production systems. Check the results afterward:

findmnt --target /mnt/data
df -h /mnt/data

Do not reboot simply to test a new mount entry when a safer validation is possible.

8. Inodes: why a disk can have free space but still fail

An inode is a filesystem data structure that tracks a file or directory's metadata, including ownership, permissions, timestamps, and references to the file's data blocks.

In simple terms, a filesystem needs both:

  • Data blocks to store file contents.
  • Inodes to track files and directories.

Two different storage limits

Disk blocks

Large log or archive files consume lots of space.

Example: most blocks used

Inodes

Huge numbers of small files consume inode entries.

Example: inode limit reached

Illustration only; the bars are not actual measurements from a server.

Check inode availability

df -i

Example:

Filesystem      Inodes   IUsed   IFree IUse% Mounted on
/dev/sda1      2621440 2621440       0  100% /

Here, the filesystem has no free inodes. Even if df -h shows several gigabytes available, creating additional files may fail.

What causes inode exhaustion?

Typical causes include:

  • An application creating thousands or millions of tiny files.
  • Temporary files that are never cleaned up.
  • Session or cache directories with uncontrolled growth.
  • Mail queues or job directories accumulating files.
  • Application code generating a separate file for every request or event.

To count files in a known application directory, including nested files:

sudo find /opt/myapp/cache -xdev -type f 2>/dev/null | wc -l

This traverses the directory and may take time on a very large tree. Replace the path with the actual directory under investigation.

To find directories containing many immediate entries:

sudo find /var/tmp -xdev -type d -print

That command lists directories; it doesn't count or rank their contents. For a real inode incident, investigate likely application cache or temporary-file directories first, then use targeted counting and sorting if necessary.

Do not delete files simply because there are many of them. Determine what creates them, whether they are still needed, and what cleanup process the application supports.

9. Realistic DevOps case study: disk full after deployment

A Python application on an Ubuntu server starts failing after a new release. Users see HTTP 500 responses, and the application logs include:

OSError: [Errno 28] No space left on device

The service may still be running, but it can no longer write logs, temporary files, caches, or application data.

Step 1 — Check capacity and inodes

df -h
df -i

Imagine the relevant filesystem reports:

Filesystem      Size Used Avail Use% Mounted on
/dev/sda1        40G  40G     0 100% /

This points to exhausted filesystem capacity. If df -i also reports 100% inode usage, there may be two problems to investigate.

Step 2 — Identify the affected mount

df -h /var/log
df -h /opt/myapp
df -h /tmp

These checks tell you which filesystem backs the directories the application may be using.

Step 3 — Find what is consuming space

If /var/log is on the affected filesystem:

sudo du -xhd1 /var/log 2>/dev/null | sort -h

Suppose the output shows that /var/log/myapp is unusually large. Inspect the directory:

sudo ls -lh /var/log/myapp/

Then inspect the relevant log's contents without making changes:

sudo tail -n 100 /var/log/myapp/app.log

If the file is huge, tail is generally preferable to printing the entire file.

Step 4 — Confirm the root cause

Suppose investigation reveals that debug logging was accidentally enabled during deployment, and the application has been writing excessively verbose messages.

The cause is not simply “Linux has a full disk.” The cause is uncontrolled log growth.

Step 5 — Recover safely

A sensible recovery plan is to:

  1. Stop the uncontrolled log growth using the application's approved configuration and deployment procedure.
  2. Preserve the incident evidence required by the organization.
  3. Follow the log-retention policy to archive or remove only approved, unneeded data.
  4. Restore sufficient free space using an approved cleanup or storage-expansion plan.
  5. Configure suitable log rotation and retention to prevent recurrence.

Avoid blindly truncating active logs, deleting entire log directories, or removing system files.

Step 6 — Verify

df -h
df -i
sudo systemctl status myapp --no-pager -l
sudo journalctl -u myapp --since "10 minutes ago" --no-pager

Test the application endpoint as well. A disk that now has free space doesn't automatically mean the application has recovered.

The diagnostic lesson

Observe

Check df -h, df -i, and the mount point.

Investigate

Use du, find, and logs to identify the actual cause.

Recover

Apply the smallest safe fix that addresses the cause.

Verify and prevent

Confirm capacity, application health, log rotation, and monitoring.

11. Safe storage troubleshooting rules

  • Never run mkfs, fdisk, parted, or destructive disk commands casually. They can destroy data or alter partitions.
  • Verify device names and UUIDs before editing /etc/fstab or mounting filesystems.
  • Don't delete files just because they are large. Check what they are, who owns them, and whether an application is using them.
  • Don't assume a reboot will fix a full disk. It can interrupt workloads and leave the underlying cause unresolved.
  • Check both blocks and inodes when a process reports that it cannot create a file.
  • Use backups and recovery plans before storage configuration changes, especially on production systems.
  • Verify after every change with df, findmnt, application health checks, and relevant logs.
