Linux for DevOps — Module 1, Lesson 19

Troubleshooting Linux Servers Systematically on Ubuntu

End-to-End Linux Systems Engineering: Performance, Monitoring, Storage & Network Diagnosis | by Zadok Ekanjume | Apr, 2026 | Medium

Welcome to Lesson 19! So far, you've learned Linux commands, permissions, users, networking, package management, systemd, logs, storage, SSH, monitoring, Bash scripting, cron, environment variables, and security hardening.

Now it's time to combine those skills into one of the most important abilities in DevOps and application support: finding the real cause of a problem without making the situation worse.

Imagine receiving this support ticket:

“The journal validation application is not responding. New delivery packages are stuck, and the server looks slow.”

Should you restart the application? Kill the process? Clear logs? Reboot the server?

Not yet. First, gather evidence.

By the end of this lesson, you'll be able to:

  • Follow a structured incident-triage process.
  • Diagnose failed services with systemctl and journalctl.
  • Investigate network, CPU, memory, disk, permissions, and configuration issues.
  • Distinguish symptoms from root causes.
  • Apply fixes safely and verify recovery.
  • Write a useful incident report for your team.

1. The troubleshooting mindset

A symptom tells you what is wrong from the user's perspective. A root cause explains why it happened.

For example:

Symptom Possible root causes
Website returns HTTP 500 Application exception, missing configuration, database failure
Website times out Network issue, firewall, overloaded server, stuck dependency
Script says “Permission denied” File permissions, directory permissions, ownership, security policy
“No space left on device” Filesystem full, inode exhaustion, quota limit
Application is slow CPU pressure, memory pressure, disk I/O, slow database, excessive concurrency
Service won't start Invalid configuration, missing executable, port conflict, permissions

One symptom can have several causes. A good troubleshooter tests the possibilities instead of guessing.

2. The incident-triage workflow

Use this workflow whenever a Linux incident occurs.

1. Define the symptom

What fails? Who is affected? When did it start?

2. Check impact and scope

One user, one app, one server, or multiple systems?

3. Collect evidence

Status, logs, processes, network, resources, recent changes

4. Test a hypothesis

Run the smallest useful diagnostic check

5. Apply a controlled fix

Change only what the evidence supports

6. Verify and document

Confirm service recovery and user impact

The six questions to ask first

  1. What exactly is failing?
  2. When did it begin?
  3. What changed recently?
  4. Is the issue affecting one component or several?
  5. What evidence supports the suspected cause?
  6. How will I confirm that the fix worked?

Golden rule: don't reboot, delete files, kill processes, or change permissions just because a system appears unhealthy. First determine what the evidence says.

3. Start with a safe health snapshot

For an incident on an Ubuntu server, begin with read-only commands.

date
hostname
uptime
whoami
free -h
df -h
df -i

Then inspect processes and services:

ps aux --sort=-%cpu | head -n 10
ps aux --sort=-%mem | head -n 10
systemctl --failed

If the application has a known service name:

sudo systemctl status myapp
sudo journalctl -u myapp -n 100 --no-pager

Replace myapp with the actual service name.

These checks give you an initial picture of time, host identity, uptime/load, memory, disk capacity, inodes, processes, failed units, and application logs.

Build an evidence timeline

Before the incident

Was the service healthy? Were jobs completing normally?

Incident begins

Record the first failure time, error messages, and user impact.

Recent change

Check deployments, configuration edits, package upgrades, or workload changes.

After remediation

Record the fix time, verification results, and remaining risk.

Use consistent time zones when comparing application logs, system logs, and monitoring timestamps. Don't assume all components log in the same time zone.

4. Troubleshooting systemd services

A Linux service may be inactive, failed, unable to start, or running but not actually serving requests.

Step 1 — Inspect the service

sudo systemctl status nginx
systemctl is-active nginx
systemctl is-enabled nginx
systemctl --failed

These commands answer different questions:

  • status shows state and recent information.
  • is-active checks whether the service is currently active.
  • is-enabled checks whether it is configured to start automatically under the applicable systemd setup.
  • --failed lists units recorded in a failed state.

A service can be active but unhealthy from the user's perspective. For example, a web server may be running while its upstream Python application is down.

Step 2 — Read the logs

sudo journalctl -u nginx -n 100 --no-pager
sudo journalctl -u nginx --since "30 minutes ago"
sudo journalctl -u nginx -p err --since today

For live troubleshooting:

sudo journalctl -u nginx -f

Press Ctrl+C to stop following logs.

Look for the earliest relevant error, not just the last message. A later error may be a consequence of the original failure.

Step 3 — Check configuration before restarting

For Nginx:

sudo nginx -t

For SSH:

sudo sshd -t

For a custom application, inspect its unit:

systemctl cat myapp

Check the executable path, service user, working directory, environment configuration, file permissions, and dependencies.

Step 4 — Restart only when justified

If you have corrected the underlying cause and a restart is appropriate:

sudo systemctl restart myapp
sudo systemctl status myapp
sudo journalctl -u myapp -n 50 --no-pager

If you changed a systemd unit file, reload the unit definitions first:

sudo systemctl daemon-reload

daemon-reload does not restart every service.

For SSH, retain the safe-change procedure from Lesson 18: validate the configuration, keep an existing connection open, and test a new session before closing the original.

5. Troubleshooting network and port problems

Suppose the application owner says:

“The application is running, but users cannot open it on port 8080.”

Don't assume the firewall is the cause. Test the connection in layers.

Network troubleshooting flowchart

Can the server be reached?

Is the application port listening?

Check with ss -lntp

Does a local request work?

Test with curl on the server

Does a remote request work?

Check routing, host firewall, and upstream rules

Step 1 — Inspect addresses and routes

ip -br addr
ip route
ip route get 1.1.1.1

These help you inspect interface addresses and routing. A route lookup toward 1.1.1.1 is a diagnostic example, not a guarantee that internet access is allowed or available.

Step 2 — Check listening ports

sudo ss -lntp

To look for port 8080 specifically:

sudo ss -lntp | grep ':8080'

Interpret the result carefully:

  • 127.0.0.1:8080 — listening on loopback only.
  • 0.0.0.0:8080 — listening on all local IPv4 interfaces.
  • A specific interface address — listening on that address.
  • No matching listener — the service may be stopped, using another port, or bound differently.

IPv6 listeners may also matter.

Step 3 — Test the service locally

curl -v --connect-timeout 3 http://127.0.0.1:8080/

Interpret common outcomes:

Result What it suggests
Connection refused Nothing is accepting the connection at that address/port, or a local rule is actively rejecting it
Connection timed out Packets may be dropped, routing may be wrong, or the service may be unresponsive
HTTP 500 An HTTP server responded, but application processing failed
HTTP 404 A server responded, but the requested route/resource was not found
HTTP 200 The endpoint returned success; application health may still require deeper checks

Step 4 — Check firewall and service configuration

sudo ufw status verbose
sudo systemctl status myapp
sudo journalctl -u myapp -n 100 --no-pager

If local requests succeed but remote requests fail, investigate the bind address, host firewall, cloud firewall, security groups, network ACLs, routing, and client path.

Do not open a port to the public internet simply to make a test succeed. First establish which sources actually need access.

6. Troubleshooting CPU, memory, and load

A slow server is not necessarily a CPU problem. You need to distinguish CPU saturation, memory pressure, storage waits, and application-level bottlenecks.

A. CPU and load average

uptime
nproc
top
ps -eo pid,ppid,user,%cpu,%mem,stat,comm --sort=-%cpu | head -n 15
  • nproc shows the number of processing units available to the command.
  • uptime displays the 1-, 5-, and 15-minute load averages.
  • top provides a live view of processes and system activity.

A high load average relative to available CPU capacity is a signal to investigate. Linux load includes runnable tasks and tasks in certain uninterruptible states, which can involve I/O waits. High load alone does not identify the cause.

B. Memory and swap

free -h
swapon --show
ps -eo pid,ppid,user,%mem,rss,comm --sort=-%mem | head -n 15

Pay particular attention to available in free -h. Linux uses spare memory for caches, so low free memory alone does not prove that the server is out of memory.

Check for sustained swap activity or evidence of an out-of-memory event. Don't kill the largest process without understanding what it does and whether it is responsible for the incident.

C. Disk I/O and pressure

If available, use:

vmstat 1 5
iostat -xz 1 5

iostat is supplied by the sysstat package on Ubuntu and may need to be installed. In vmstat, examine subsequent samples rather than relying only on the first report, which can reflect averages since boot.

Storage latency and queueing can make an application slow even when CPU usage is modest. Interpret I/O metrics in context; a single utilization percentage is not a universal saturation threshold.

A useful decision guide

CPU-bound

High sustained CPU usage. Inspect top processes, concurrency, recent code or rule changes, and throughput.

Memory pressure

Low available memory, swap activity, or OOM events. Inspect process memory, workload size, and leaks.

I/O bottleneck

High wait or storage latency. Check the affected filesystem, disk activity, logs, and workload pattern.

7. Troubleshooting disk-space and inode problems

Disk incidents often cause application failures, logging problems, and deployment issues.

Step 1 — Check capacity and inodes

df -h
df -i
  • df -h shows filesystem space usage.
  • df -i shows inode usage.

A filesystem can have free gigabytes but no available inodes for new files.

Step 2 — Identify where space is used

sudo du -xhd1 /var 2>/dev/null | sort -h
sudo du -xhd1 /var/log 2>/dev/null | sort -h

These commands summarize directory usage while staying on the same filesystem (-x). They can take time on large filesystems.

To inspect a particular application:

sudo du -sh /opt/myapp

Step 3 — Investigate before deleting

Look for:

  • Unexpectedly large application logs.
  • Temporary files or caches that are safe to regenerate.
  • Old artifacts retained beyond their intended lifecycle.
  • Deleted files still held open by a running process.
  • Inode exhaustion caused by large numbers of small files.

For deleted-open files, if lsof is installed:

sudo lsof +L1

A process may still occupy disk space after a file has been deleted. Identify the process and its purpose before taking action.

Never use rm -rf as your first disk-space fix. Preserve incident evidence, follow retention policy, and use approved cleanup or log-rotation procedures. Deleting a log file does not necessarily free its space immediately if a process still has it open.

8. Troubleshooting permissions and configuration

Consider this error from a scheduled validation script:

/opt/myapp/run_validation.sh: Permission denied

Several different issues can produce permission errors. Work through them systematically.

Step 1 — Check the file and parent directories

ls -l /opt/myapp/run_validation.sh
namei -l /opt/myapp/run_validation.sh

The user running the command needs appropriate access to the file and search (x) permission on every parent directory.

Step 2 — Confirm the execution context

whoami
id

For a systemd service, also inspect:

systemctl cat myapp
sudo systemctl status myapp

Check the configured User=, Group=, WorkingDirectory=, and ExecStart= values, if present.

For cron, inspect the relevant user's crontab:

crontab -l

A command that succeeds as your login user may fail under another account because ownership, environment, and working directory differ.

Step 3 — Check the interpreter and configuration

For a Bash script:

head -n 5 /opt/myapp/run_validation.sh
bash -n /opt/myapp/run_validation.sh

Check whether the interpreter exists, whether the file uses the expected line endings, and whether the application configuration is present and readable.

A script can be run with bash script.sh even if it does not have the executable bit, provided the invoking user can read the file. Running ./script.sh generally requires executable permission and a valid interpreter line.

Step 4 — Check mount and security restrictions

If the file permissions look correct but execution still fails, investigate:

findmnt /opt/myapp

A filesystem mounted with noexec can prevent direct execution from that mount. Security policies such as AppArmor may also restrict access. Don't disable a security control merely to bypass an error; determine the policy and intended behavior first.

Step 5 — Fix the actual problem

Choose the smallest change that resolves the diagnosed cause. For example, if an approved application script is meant to be executable by its owner:

chmod u+x /opt/myapp/run_validation.sh

Only run that change if the file's owner and intended access are correct. Do not use chmod 777.

After the change, test as the appropriate service account where practical and inspect application logs.

9. Four realistic DevOps troubleshooting case studies

Case study A — Python web application returns HTTP 500

Ticket: The service is running, but every API request returns HTTP 500.

Start with:

sudo systemctl status myapp
sudo journalctl -u myapp --since "30 minutes ago" --no-pager
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/

Suppose the log shows:

KeyError: 'DATABASE_URL'

Evidence-based conclusion: the application expects a configuration variable that is missing or not loaded.

Safe next steps:

  1. Inspect the service unit and configuration-loading logic.
  2. Confirm the intended configuration source.
  3. Check that the service account can access the required file or secret.
  4. Supply the correct configuration through the approved mechanism.
  5. Restart the service only if the change requires it.
  6. Test the endpoint and review fresh logs.

Do not invent a database URL or put credentials directly into the incident report.

Case study B — The validation queue is growing

Ticket: Perl validation jobs that usually finish in minutes now take 25 minutes.

Collect:

uptime
nproc
free -h
ps aux --sort=-%cpu | head -n 10
vmstat 1 5

Suppose the evidence shows sustained CPU usage by the Perl validator, sufficient available memory, no sustained swap activity, and no obvious I/O queue buildup.

Investigate recent changes to worker concurrency, XML processing, rule execution, and input volume.

Possible root cause: a deployment increased concurrency, causing too many CPU-intensive validation jobs to run simultaneously.

Potential remediation: test a reduced worker count in a controlled way, compare throughput and queue growth, and follow the team's change process.

Do not kill active validation jobs without understanding the impact on delivery data and job recovery.

Case study C — Disk fills and the service stops writing logs

Ticket: The application reports:

OSError: [Errno 28] No space left on device

Run:

df -h
df -i
sudo du -xhd1 /var/log 2>/dev/null | sort -h

Suppose /var/log/myapp is unexpectedly large following a debugging deployment.

Evidence-based response:

  1. Confirm whether filesystem blocks or inodes are exhausted.
  2. Identify which log files are growing and why.
  3. Preserve relevant evidence and follow retention policy.
  4. Correct excessive logging and configure appropriate rotation.
  5. Use approved cleanup procedures.
  6. Verify free capacity and service behavior.

Deleting arbitrary system files or rebooting the server is not a reliable fix.

Case study D — Cron reports permission denied

Ticket: A scheduled report runs successfully when launched manually but fails every morning.

Compare the two execution contexts:

whoami
id
crontab -l

Inspect the script and its parent directories:

ls -l "$HOME/devops-lab/health_check.sh"
namei -l "$HOME/devops-lab/health_check.sh"

Also check the cron log and output file. The scheduled job may run as a different user or lack access to a directory or log destination.

Possible resolution: correct the intended owner or permissions, or adjust the job to use the proper service account and output path.

Verify the next scheduled run. A successful manual test alone is not proof that cron is fixed.
