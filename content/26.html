Module 1, Lesson 25 — Production Capstone: Incident Response

Level: Intermediate · Estimated time: 45–60 minutes · Practical focus: end-to-end troubleshooting

This capstone brings everything together. You’ll investigate a simulated broken application, find the root cause, restore service, verify recovery, and write an incident report — exactly like a real DevOps on-call incident.

1. The scenario

You receive an alert:

“The delivery-tracking application is slow. Customers cannot place orders.”

The application runs on Ubuntu behind Nginx, with a Python backend and systemd service tracker.service.

2. Incident triage workflow

Follow this order — do not restart or reboot until you have evidence:

  1. Define the symptom — what fails, who is affected, when did it start?
  2. Check scope — one user, one app, one server, or many?
  3. Collect evidence — logs, service status, CPU/memory/disk, network.
  4. Form a hypothesis — test one change at a time.
  5. Apply a fix — minimal, reversible change.
  6. Verify recovery — confirm the symptom is gone.
  7. Document — write an incident report.

3. Step-by-step investigation

Step 1 — Confirm the symptom

curl -I http://localhost
curl -w "@curl-format.txt" -o /dev/null -s http://localhost

If the site times out or returns 500, the application or Nginx is failing.

Step 2 — Check the service

systemctl status tracker.service
systemctl status nginx

Look for: inactive, failed, activating, or crash-loop.

Step 3 — Inspect logs

journalctl -u tracker.service --since "30 minutes ago"
tail -n 50 /var/log/tracker/app.log
sudo tail -n 50 /var/log/nginx/error.log

Search for errors:

grep -inE "error|traceback|failed|timeout|connection refused" /var/log/tracker/app.log

Step 4 — Check system resources

df -h
free -h
top -n 1

Common culprits: full disk, memory pressure, high CPU.

Step 5 — Form and test a hypothesis

Example: The tracker service crashed because the log disk is full.

Fix (minimal and reversible):

sudo systemctl restart tracker.service

Then confirm:

systemctl status tracker.service
curl http://localhost

Step 6 — Verify recovery

  • The service is active (running).
  • curl returns HTTP 200.
  • New orders are being processed (check recent log entries).

Step 7 — Write the incident report

Template:

Title: Delivery-tracking application outage
Date: 2026-10-27
Duration: 18 minutes
Impact: Customers could not place orders
Root cause: tracker.service crashed after /var/log filled to 100%
Fix: Cleared old logs, restarted tracker.service
Prevention: Add log rotation and disk monitoring alert
Timeline:
  10:00 Alert received
  10:05 Investigated logs, found disk full
  10:12 Cleared logs, restarted service
  10:18 Service verified, incident closed
