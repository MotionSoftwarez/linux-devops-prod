3. Display file contents with cat

The simplest way to read a small text file is:

cat app.conf

Example output:

APP_ENV=production
APP_PORT=8080
LOG_LEVEL=info

Read a system file:

cat /etc/hostname

This typically prints the system's hostname.

You can also display multiple files consecutively:

cat first.txt second.txt

When to use cat: Small configuration files, short text files, and quick checks.

When not to use it: Very large logs, because thousands of lines can flood the terminal.

Security tip: configuration files and logs can contain API keys, passwords, tokens, or personal information. Check for sensitive content before sharing output.

4. Browse large files with less

Use less to inspect a file page by page:

less /var/log/syslog

The file may not exist on every distribution. On some systems, application and system logs are available through journalctl instead.

Practise with a file available on most Linux systems:

This file contains account information, not passwords in readable form. However, it can reveal usernames and system details, so don't publish its contents unnecessarily.

5. Read the beginning of a file with head

head displays the first 10 lines by default.

head app.log

Show only the first five lines:

head -n 5 app.log

DevOps example

When an application starts, its log may record initialization messages at the beginning. Inspect the first 20 lines:

head -n 20 app.log

This helps you check startup information without reading the entire file.

6. Read recent entries with tail

tail displays the last 10 lines by default.

tail app.log

Show the last 25 lines:

tail -n 25 app.log

Monitor a log in real time

tail -f app.log

This keeps running and displays new lines as they are appended to the file. It's useful when reproducing a bug or watching an application restart.

  • Press Ctrl+C to stop following the log.
  • tail -F app.log can be useful when the log file is rotated or recreated.

Example: live application log

[10:31:02] INFO Server started on port 8080

[10:31:04] INFO Request received

[10:31:05] WARN Database response slow

[10:31:07] ERROR Database connection refused

[10:31:09] INFO Retry scheduled

Illustrative log entries, not output from a real server.

Remember: head looks at the beginning; tail looks at the end.

7. Find errors using grep

grep searches for lines that match a word or pattern.

Search for ERROR:

grep "ERROR" app.log

Ignore uppercase and lowercase:

grep -i "error" app.log

Show line numbers:

grep -n "ERROR" app.log

Search for multiple possible problems:

grep -inE "error|failed|timeout" app.log

This searches case-insensitively for any of the three terms.

Search recursively through a directory:

grep -rni "database" ./logs/

Count matching lines:

grep -c "ERROR" app.log

Combine commands with a pipe

Suppose app.log contains 50,000 lines, but you want errors from only the last 100 lines.

tail -n 100 app.log | grep -i "error"

The | symbol is called a pipe. It sends the output from one command into another command.

app.log

Thousands of lines

tail -n 100

Select the last 100 lines

grep -i "error"

Keep only matching error lines

Useful grep options

Option Meaning
-i Ignore letter case
-n Display line numbers
-r Search recursively
-v Display lines that don't match
-E Use extended regular expressions
-c Count matching lines

A search that returns no matches doesn't necessarily mean no problem exists. The log path, time range, terminology, or logging level may be different.

8. Edit files with nano

nano is a beginner-friendly text editor that works inside the terminal.

Open or create a file:

nano app.conf

Example configuration:

APP_ENV=development
APP_PORT=8080
LOG_LEVEL=debug

You can use the arrow keys to move around, type to edit, and use the shortcuts below.

Ctrl + O

Save (write out) the file

Enter

Confirm the filename when saving

Ctrl + X

Exit nano

Ctrl + W

Search within the file

Safe editing workflow

Before editing an important configuration:

cat app.conf
cp -i app.conf app.conf.bak
nano app.conf

After editing:

  1. Save and exit.
  2. Review the changes.
  3. Validate the configuration using the application's supported test command.
  4. Apply the change according to your team's deployment procedure.

Production safety: Editing a file does not guarantee that its syntax is valid. Don't restart a critical service until you have checked the configuration and followed the relevant change process.

9. Realistic DevOps case study: troubleshoot a failing application

Scenario: A web application is returning errors. You suspect the database connection, but you don't yet know the cause.

For this exercise, assume the application log is /var/log/myapp/app.log and its configuration is /etc/myapp/app.conf. These are example paths; your actual application may use different locations.

Step 1 — Inspect recent log entries

tail -n 50 /var/log/myapp/app.log

Look for recent warnings and errors.

Step 2 — Search for likely causes

grep -inE "error|failed|database|timeout" /var/log/myapp/app.log

This filters the log for useful clues and shows line numbers.

Step 3 — Inspect the surrounding context

less /var/log/myapp/app.log

Inside less, type /database and press Enter. Press n to find the next match, then inspect the lines around it.

Step 4 — Check the configuration file

First verify that the file exists:

ls -l /etc/myapp/app.conf

If authorized, inspect it:

less /etc/myapp/app.conf

Be careful not to expose credentials or tokens when viewing or sharing the output.

Step 5 — Make changes only when evidence supports them

If an authorized engineer confirms that a setting needs to change, make a backup and edit the file:

sudo cp -i /etc/myapp/app.conf /etc/myapp/app.conf.bak
sudo nano /etc/myapp/app.conf

Then use the application's documented validation command before applying the change.

Troubleshooting decision tree

Application reports an error

Inspect recent logs using tail

Search using grep

Error found

Use less to examine nearby log entries.

No match found

Verify the path and time range; check the service journal if appropriate.

Confirm the cause before changing configuration

An error message is a clue, not always the root cause. A database connection failure could be caused by network issues, an unavailable database, incorrect settings, credentials, or access rules.

Six habits of a good DevOps engineer

  1. Use cat for small files and less for large ones.
  2. Use tail to investigate recent events.
  3. Use grep to narrow down large amounts of log output.
  4. Use tail -f when monitoring an issue as it happens.
  5. Back up important configuration files before editing.
  6. Validate changes and protect sensitive log data before applying or sharing anything.
