Linux package management on Ubuntu with apt

Beginner friendly

Ubuntu / Debian

DevOps fundamentals

In this lesson, you’ll learn how to install software, update packages safely, manage repositories, resolve dependency problems, and install DevOps tools without unnecessarily risking a server.

1. What is package management?

Imagine an Ubuntu server is a workshop. You need tools such as Python, Git, Nginx, or curl to do your work.

You could download each tool manually, find its dependencies, configure it, and update it yourself. Or you can use a package manager that handles much of that work for you.

Ubuntu’s primary command-line package-management tool is apt.

Your request

“Install Git on this server.”

APT package manager

Checks package information, dependencies and available versions

Repositories

Where package metadata and downloadable packages are published

Installed system

Files, binaries, libraries and configuration

Understand these four terms

  • Package: a software bundle, usually a .deb file on Ubuntu.
  • Repository: a configured software source that publishes package indexes and packages.
  • Dependency: another package required by the software.
  • Package manager: the tool that installs, upgrades, and removes packages while tracking their relationships.

apt is the user-facing package-management command. dpkg is the lower-level tool that works with Debian packages and installed-package records.

2. The most important apt workflow

The first commands to learn are:

Command Purpose
sudo apt update Refresh available-package information
apt list --upgradable Show packages with available upgrades
sudo apt install git Install Git
sudo apt remove git Remove Git while generally retaining its configuration files
sudo apt purge git Remove Git and its package-managed configuration files
sudo apt autoremove Remove automatically installed packages that are no longer needed
apt show git Show information about the Git package
dpkg -l git Check the installed-package record for Git

Critical distinction: apt update does not upgrade installed software. It refreshes the local package indexes. apt upgrade is the command that upgrades installed packages.

3. Update packages safely

Before installing software or troubleshooting a package version, refresh the package index.

sudo apt update

This downloads updated package lists from your configured repositories. It does not install every available update.

Next, inspect what can be upgraded:

apt list --upgradable

Upgrade installed packages:

sudo apt upgrade

APT normally avoids removing installed packages to complete this standard upgrade. Review the proposed changes before confirming.

What about full-upgrade?

sudo apt full-upgrade

This can install or remove packages when needed to complete an upgrade. It is more disruptive than a standard upgrade, so inspect the proposed changes carefully, especially on production servers.

Safe production habit

Check maintenance windows, backups or snapshots, disk space, service impact, and the proposed APT transaction before upgrading critical servers.

A routine package update can still restart services or introduce compatibility changes, depending on the packages involved.

Practice: predict the result

You run sudo apt update. What should you expect?

All installed software is upgraded immediately.

APT refreshes package indexes from configured repositories.

APT removes old packages automatically.

4. Install, inspect, and remove packages

Let’s use Git as an example. These commands are intended for an Ubuntu server where you have appropriate administrative access.

Install a package

sudo apt install git

To install several packages together:

sudo apt install git curl unzip

APT will display the packages to be installed, dependencies, download size, and additional disk space required. Read the summary before accepting.

Check the package

git --version
apt show git
dpkg -s git
apt-cache policy git

These commands answer different questions:

  • git --version: which Git version runs when invoked.
  • apt show git: package description and metadata.
  • dpkg -s git: installed package status and version, if installed.
  • apt-cache policy git: installed and repository candidate versions, where available.

Search for software

apt search nginx
apt show nginx

Search results may include packages that are not installed. Searching is not the same as installing.

Remove software

sudo apt remove git

This generally removes the package but leaves package-managed configuration files behind.

To remove the package and its package-managed configuration:

sudo apt purge git

To remove automatically installed dependencies that are no longer required:

sudo apt autoremove

Important: Purging does not guarantee that every application-created file, user data, database, log, or file under a custom directory will be deleted. Conversely, it is not a backup mechanism. Inspect what APT proposes to remove before confirming.

Visual: package lifecycle

Search / inspect

apt search, apt show, apt-cache policy

Install

sudo apt install package-name

Maintain

sudo apt update → inspect upgrades → sudo apt upgrade

Remove if no longer needed

remove, purge, or reviewed autoremove

5. Repositories: where packages come from

APT does not magically know about every application on the internet. It uses repositories configured on the machine.

On modern Ubuntu systems, repository configuration commonly appears in:

  • /etc/apt/sources.list
  • /etc/apt/sources.list.d/ — files such as .list or .sources

Inspect your configuration:

ls -l /etc/apt/sources.list.d/
cat /etc/apt/sources.list

Some Ubuntu installations use the newer deb822 .sources format and may not have an active /etc/apt/sources.list. To inspect both common locations:

grep -R -nE '^(deb |Types:|URIs:|Suites:|Components:|Signed-By:)' \
  /etc/apt/sources.list /etc/apt/sources.list.d/ 2>/dev/null

A missing sources.list file can be normal; the command may report that it cannot read it. Check the .sources files as well.

How repository configuration works

Repository configuration

Repository URI + Ubuntu release (suite) + components + signing key

sudo apt update

Fetches metadata and verifies repository signatures

APT package index

Available versions and dependency information

What do repository components mean?

Ubuntu archives commonly divide software into components such as main, universe, restricted, and multiverse. Availability and support differ between components. Third-party repositories have their own configuration and trust arrangements.

To see which version APT would select:

apt-cache policy nginx

If a package is unavailable, investigate before adding random repositories:

apt search nginx
apt-cache policy nginx
sudo apt update

Safe repository practices

  1. Prefer Ubuntu's official repositories when they meet your requirements.
  2. For third-party software, use the vendor's official installation documentation and verify the domain.
  3. Verify signing keys and use repository-scoped key configuration, commonly with Signed-By.
  4. Do not disable package signature verification just to make an installation succeed.
  5. Avoid obsolete apt-key instructions; it is deprecated.
  6. Never switch a production machine to a different Ubuntu release's repository just to obtain a newer package.
  7. Review repository changes and the output of sudo apt update before installing anything.

If you add or change a repository, run sudo apt update afterwards so APT refreshes its package metadata.

6. Dependencies: why installing one tool may install several packages

Suppose a command-line application requires two libraries. Those libraries may require other packages.

Application: Tool A

Library B

Dependency

Library C

Dependency

APT resolves dependencies and proposes the required package operations.

Inspect dependencies:

apt-cache depends git

Simulate an installation without actually installing packages:

apt-get -s install nginx

The -s flag asks APT to simulate the transaction. This is useful for checking which packages it would install, upgrade, or remove.

Common dependency problems

Symptom What to investigate
Unable to locate package Package name, enabled repositories, and package indexes
404 Not Found during download Stale metadata or a repository mirror issue; refresh indexes and retry
Unmet dependencies Repository consistency, pinned versions, and package availability
Could not get lock Another package-management process may be running
dpkg was interrupted The previous package transaction may not have completed

If a package-management lock is present, first check whether another APT or dpkg process is actively working:

ps -ef | grep -E '[a]pt|[d]pkg'

Do not delete lock files as a first response. Interrupting an active package transaction can leave the system in an inconsistent state.

If a transaction was interrupted and no package manager is running, a typical recovery command is:

sudo dpkg --configure -a

Then, if needed, inspect and repair dependency issues with:

sudo apt --fix-broken install

These commands can change system state. Review the output and understand the proposed operations before confirming; use your organization's recovery procedure on production servers.

7. Safely install DevOps tools

Common Ubuntu tools you may use while supporting applications and deployments include:

Tool Typical purpose
git Version control
curl HTTP/API requests and troubleshooting
jq Read and filter JSON
unzip Extract ZIP archives
tree View directory structures
nginx Web server and reverse proxy
python3-venv Create isolated Python environments

Before installing, check the OS version and package availability:

cat /etc/os-release
apt-cache policy jq
apt-get -s install jq

If the package and proposed transaction look appropriate:

sudo apt update
sudo apt install jq
jq --version

What about installing software with curl | bash?

You may see installation instructions like:

curl -fsSL https://example.com/install.sh | sudo bash

This downloads a script and executes it immediately with administrative privileges. The example domain is illustrative, not a real installer.

Safer approach: download the script from the verified official source, inspect it, verify its integrity or signature when the vendor provides a mechanism, and understand what it changes before executing it. A script may modify repositories, add signing keys, install services, or alter system configuration.

APT is often preferable when an official, suitable repository is available because it provides package metadata, dependency handling, and package records. However, APT is not automatically safe merely because it is APT: repository trust still matters.

Is sudo always required?

No. Reading package information generally does not require root privileges. Installing or removing system packages usually does.

Use the minimum permissions required. Do not run every command as root, and do not use sudo to bypass errors you have not investigated.

8. Real-world DevOps case study: Nginx deployment fails

Scenario

A team is deploying a web application on an Ubuntu server. The deployment script fails because Nginx is missing. Someone suggests running a large, unreviewed installation script as root.

Your job is to install the needed package using a controlled process.

Step 1 — Confirm the environment

cat /etc/os-release
apt-cache policy nginx

Verify the OS release and see whether APT knows about Nginx.

Step 2 — Refresh package metadata

sudo apt update

If repository errors appear, diagnose those first rather than blindly adding a new source.

Step 3 — Preview the transaction

apt-get -s install nginx

Check the planned installation, dependency changes, and any proposed removals.

Step 4 — Install and verify

sudo apt install nginx
nginx -v
sudo systemctl status nginx --no-pager

Confirm the installed version and service status. Installation does not guarantee that the site is configured correctly or reachable remotely.

Step 5 — If it fails, investigate

sudo journalctl -u nginx --since "15 minutes ago"
sudo nginx -t

Review service logs and test Nginx configuration syntax. Avoid reinstalling repeatedly before identifying the cause.

Production lesson: package installation, service configuration, service health, and network accessibility are four different checks. Passing one does not guarantee that the others pass.

14. Key takeaways

  • apt update refreshes package metadata; apt upgrade upgrades installed packages.
  • Use apt show, apt-cache policy, and simulation to investigate before making changes.
  • Repository configuration and signing keys are part of your server's security boundary.
  • APT resolves available dependencies, but repository conflicts and interrupted transactions still need careful diagnosis.
  • On production systems, review proposed changes, plan recovery, and verify both package status and application health.
