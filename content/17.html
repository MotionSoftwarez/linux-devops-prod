1. What is cron?

Cron is a time-based job scheduler commonly used on Linux systems. You specify when a command should run, and a cron service launches it at the scheduled time.

For example, you can schedule a health-check script to run every 15 minutes, a report to run every morning, or a backup script to run every Sunday.

Cron schedule

Every 15 minutes

Cron service

Checks configured schedules and launches due jobs

Bash script runs

Checks disk usage and service state

Output and exit status

Logs support monitoring and troubleshooting

Cron versus Bash

  • Bash script: defines what actions to perform.
  • Cron schedule: defines when to start the script.
  • Cron daemon: manages scheduled execution.
  • Log file: records output so you can investigate what happened.

Cron is not a replacement for a service manager such as systemd. Cron is useful for time-based tasks; systemd services are often a better fit for applications that must stay running continuously.

2. Cron syntax: understand the five fields

A standard user crontab entry has five time fields followed by the command.

Example cron expression

*/15 * * * *

Run every 15 minutes

1

Minute

0–59

2

Hour

0–23

3

Day

1–31

4

Month

1–12

5

Weekday

In the weekday field, 0 and 7 commonly both mean Sunday; 1 is Monday.

The five fields are separated by spaces. After them comes the command to execute.

Symbols you'll use frequently

Symbol Meaning Example
* Every allowed value * * * * * — every minute
*/n Every n units */15 * * * * — every 15 minutes
, Several specific values 0 9,17 * * * — 9 AM and 5 PM
- A range 0 9-17 * * * — hourly at minute 0, 9 AM through 5 PM
n A specific value 30 8 * * * — 8:30 AM daily

Cron times use the machine's configured local time zone unless the implementation or configuration specifies otherwise.

3. Common cron schedules

Here are useful examples for Ubuntu and DevOps tasks.

Cron expression Schedule
* * * * * Every minute
*/5 * * * * Every 5 minutes
*/15 * * * * Every 15 minutes
0 * * * * At the start of every hour
30 8 * * * Every day at 8:30 AM
0 2 * * * Every day at 2:00 AM
0 9 * * 1-5 At 9 AM Monday through Friday
0 6 * * 0 Every Sunday at 6 AM
0 0 1 * * Midnight on the first day of every month

A few things to remember:

  • 0 2 * * * means 2:00 AM, not every two hours.
  • 0 */2 * * * means every two hours, on the hour.
  • */10 * * * * means every 10 minutes, not 10 minutes after every script completion.
  • A job scheduled at a time that doesn't exist during a daylight-saving clock change may be skipped, depending on the cron implementation.

4. User crontabs: schedule jobs for your account

A user crontab contains schedules that run as the user who owns that crontab.

For example, if you edit your own crontab, jobs normally run with your user's permissions—not automatically as root.

Step 1 — Check the cron service

On Ubuntu:

systemctl status cron

If cron is installed but inactive and you have permission to administer the machine:

sudo systemctl enable --now cron

Check again:

systemctl is-active cron
systemctl is-enabled cron

is-active checks the current state; is-enabled checks whether the service is configured to start automatically.

Step 2 — Open your crontab

crontab -e

The first time, Ubuntu may ask you to select an editor. Choose Nano if you are not comfortable with Vim.

Add this harmless test job:

* * * * * /usr/bin/date >> /tmp/cron-learning.log 2>&1

Save and exit. Wait a minute, then inspect the log:

tail -n 10 /tmp/cron-learning.log

You should see timestamps appended as the job runs.

This is a learning exercise, not a recommended production schedule: every-minute jobs should be used only when needed.

Step 3 — Manage your crontab

crontab -l

Lists your current jobs.

crontab -e

Edits your jobs.

crontab -r

Removes your entire user crontab. Avoid running this casually; it can delete every schedule configured in that crontab.

To remove only the learning job, use crontab -e and delete just that entry.

5. User cron versus system cron

Ubuntu offers several places to configure scheduled tasks.

Location Typical purpose Runs as
crontab -e Personal or application-user jobs Crontab owner
/etc/crontab System-wide schedules User specified in each entry
/etc/cron.d/ Separate system/application schedule files User specified in each entry
/etc/cron.hourly/ Scripts intended for hourly execution Depends on the system's cron configuration
/etc/cron.daily/ Daily maintenance scripts Depends on the system's cron configuration
/etc/cron.weekly/ Weekly maintenance scripts Depends on the system's cron configuration
/etc/cron.monthly/ Monthly maintenance scripts Depends on the system's cron configuration

The crucial syntax difference is that /etc/crontab and files in /etc/cron.d/ include an additional username field before the command.

User crontab:

0 2 * * * /opt/myapp/backup.sh

System crontab entry:

0 2 * * * backupuser /opt/myapp/backup.sh

The second line runs as backupuser, assuming that account exists and has the required permissions.

Files in /etc/cron.d/ should follow the system's expected format and naming rules. They generally need to be owned by root and not be writable by other users.

Special schedules

Some cron implementations support shortcuts such as:

@reboot /opt/myapp/startup-check.sh
@daily /opt/myapp/daily-report.sh
@weekly /opt/myapp/weekly-report.sh

@reboot means when the cron service starts, rather than exactly at a daily time. It is not a substitute for configuring a long-running application as a systemd service.

6. The most common cron problem: the environment is different

When you run a command interactively, your terminal usually provides a richer environment than cron does.

Your terminal might have:

  • A customized PATH
  • Variables loaded by shell startup files
  • A familiar working directory
  • A virtual environment activated manually
  • Functions or aliases
  • Access to files available only to your interactive user

Cron generally does not start your usual interactive shell session.

Interactive shell versus cron

Terminal

Your configured PATH

Interactive settings

Often your project directory

Cron

Minimal environment

Different PATH

Usually not your project directory

Result: a script that works in your terminal may fail when scheduled.

Problem A — Command not found

This may work in your terminal:

python3 /opt/myapp/report.py

But a scheduled task may not find python3 if its directory isn't in cron's PATH.

Find the executable's path in your terminal:

command -v python3
command -v bash
command -v flock

Then use the actual absolute paths in your script or crontab. On many Ubuntu systems, these commands resolve to paths such as /usr/bin/python3, /usr/bin/bash, and /usr/bin/flock, but verify your own machine.

Problem B — Wrong working directory

This script is fragile:

#!/usr/bin/env bash
python3 report.py

If cron starts the script outside the project directory, Python may not find report.py.

A more reliable approach:

#!/usr/bin/env bash
set -Eeuo pipefail

cd /opt/myapp
/usr/bin/python3 /opt/myapp/report.py

An absolute script path is even clearer:

/usr/bin/python3 /opt/myapp/report.py

The Python script may still depend on files or relative paths, so its working directory and configuration should be considered explicitly.

Problem C — Missing environment variables

Suppose your application requires:

export APP_ENV=production

Don't assume that variable exists when cron runs.

You can set non-secret variables in the crontab:

APP_ENV=production

However, credentials should not be casually embedded in a crontab or script. Prefer an approved secrets mechanism or a protected configuration file readable only by the service account.

For Python applications, use the project's virtual environment explicitly:

/opt/myapp/venv/bin/python /opt/myapp/report.py

This avoids relying on whichever Python happens to be selected by the environment.

7. Logging and output redirection

Cron jobs run without a normal terminal attached, so you need a way to capture their output.

Remember the two main output streams:

  • stdout (file descriptor 1): normal output.
  • stderr (file descriptor 2): error messages.

Common redirection patterns

Syntax Purpose
> output.log Write stdout, replacing the file
>> output.log Append stdout to the file
2> errors.log Write stderr to a file
2>&1 Redirect stderr to the current stdout destination
> job.log 2>&1 Send both stdout and stderr to one log
>/dev/null 2>&1 Discard both output streams

Order matters. For example, > job.log 2>&1 sends both streams to the log. Reversing the order can leave stderr going to its original destination.

Example: capture a daily report

30 8 * * * /opt/myapp/daily_report.sh >> /var/log/myapp/daily_report.log 2>&1

This runs daily at 8:30 AM and appends output to the log.

For a production job, confirm that the cron user can write to the log file and traverse its parent directories. Also configure log rotation so the file doesn't grow forever.

Capture output during learning

Try this in your own crontab:

*/5 * * * * /usr/bin/date >> /tmp/cron-learning.log 2>&1

Wait five minutes or more, then run:

tail -n 20 /tmp/cron-learning.log

For a script that reports an error and exits nonzero, capture both streams so the reason is available for troubleshooting.

8. Prevent overlapping jobs with flock

Imagine a report normally takes two minutes to run, but one day it takes 20 minutes. If cron starts the same report every five minutes, several copies may run simultaneously.

This can cause:

  • Duplicate processing
  • High CPU or memory use
  • Competing writes to the same files
  • Inconsistent reports
  • An increasing backlog of jobs

The solution: use a lock

On Ubuntu, flock from the util-linux package is commonly available. It can provide a simple lock around a command.

Example crontab entry:

*/5 * * * * /usr/bin/flock -n /tmp/myapp-report.lock /opt/myapp/report.sh >> /var/log/myapp/report.log 2>&1

How it works:

  • -n means do not wait if the lock is already held.
  • If another instance has the lock, the new invocation doesn't start the command.
  • The lock is released when the process holding it exits and closes the lock descriptor.

Verify the actual flock path with command -v flock before using this exact entry.

Cron triggers the job

Attempt to acquire lock

Lock available

Run job

Lock held

Skip this run

Important details about locks

  • Every instance must use the same lock file to coordinate with each other.
  • Choose a directory with suitable permissions and appropriate persistence for your use case.
  • Don't manually delete a lock file just because it exists. With flock, the file's existence alone does not mean a lock is held.
  • flock helps prevent overlapping executions on a shared lock, but it doesn't protect against duplicate work caused by crashes, partial transactions, or separate hosts unless your design handles those cases.

9. Safe scheduling: a production checklist

Before putting a scheduled job on a real Ubuntu server, check the following.

The script has been tested manually with the intended service account.

The crontab uses the correct time zone and schedule.

Commands and important file paths are absolute where practical.

Required directories, permissions, and configuration are checked.

The job captures useful output and error messages.

The job cannot accidentally delete or overwrite unrelated data.

Overlapping execution has been considered and controlled where necessary.

Logs have a retention or rotation policy.

Failures can be detected and investigated.

The job has a documented owner and purpose.

0 of 10 safety checks completed

A good scheduled job should be predictable, observable, and safe to repeat. For tasks such as package processing, backups, and deployment, consider whether a partially completed run could be repeated without causing damage.

10. Realistic DevOps case study: schedule the Lesson 15 health check

Scenario

Your Ubuntu server runs a journal delivery validation application. You want to check:

  • Root filesystem usage
  • Whether the selected system service is active
  • Whether the health-check script completed successfully
  • What happened if the job failed overnight

You created the health-check script in Lesson 15 at:

~/devops-lab/health_check.sh

For a scheduled job, use a stable absolute path, not ~, because cron doesn't expand ~ in every context as you might expect.

Step A — Prepare a dedicated location

For this learning exercise, use your own home directory and a log folder:

mkdir -p "$HOME/devops-lab/logs"
chmod 700 "$HOME/devops-lab"
chmod 700 "$HOME/devops-lab/logs"

Find your actual home directory:

printf '%s\n' "$HOME"

Confirm that the health-check script exists:

ls -l "$HOME/devops-lab/health_check.sh"
bash -n "$HOME/devops-lab/health_check.sh"

If you created the script under a different directory in Lesson 15, adjust the paths accordingly.

Step B — Test the script manually

Run it before scheduling:

bash "$HOME/devops-lab/health_check.sh" cron 80
echo "Exit status: $?"

If it reports that the cron service is inactive, investigate the service rather than assuming the script itself is broken. The script reports status; it does not repair the system.

Step C — Schedule it every 15 minutes

Open your user crontab:

crontab -e

Add the following entry, replacing /home/YOUR_USER with the actual absolute path printed by printf '%s\n' "$HOME":

*/15 * * * * /usr/bin/flock -n /tmp/health-check.lock /usr/bin/bash /home/YOUR_USER/devops-lab/health_check.sh cron 80 >> /home/YOUR_USER/devops-lab/logs/health-check.log 2>&1

This is a template: substitute your actual username and verify the executable paths first.

For example, you can check:

command -v bash
command -v flock
command -v systemctl

The example uses a lock so a slow health check won't overlap with another invocation using the same lock.

Production consideration: /tmp is suitable for many simple single-host learning jobs, but lock-file placement and permissions should be chosen deliberately on production systems.

Step D — Verify the schedule

Confirm the crontab contains your entry:

crontab -l

Wait for the next scheduled time and inspect the log:

tail -n 50 "$HOME/devops-lab/logs/health-check.log"

If you need to watch a run live:

tail -f "$HOME/devops-lab/logs/health-check.log"

Press Ctrl+C to stop following the log. It doesn't stop the scheduled job.

Step E — Understand what success means

The health-check script returns:

  • 0 if its implemented checks pass.
  • 1 if a check or prerequisite fails.
  • 2 for an invalid threshold.

The log tells you what happened during execution, while the exit status tells the calling process whether the script succeeded. Cron itself does not automatically turn every nonzero status into an alert. You need a monitoring or notification mechanism if failures must page someone.

This is an operationally useful distinction: a scheduled job running is not the same as the job succeeding.

11. Troubleshooting cron jobs on Ubuntu

If a scheduled job doesn't run, troubleshoot in layers rather than changing multiple things at once.

1. Is the cron service running?

systemctl is-active cron
systemctl status cron

If it is inactive, inspect why before enabling or restarting it.

2. Is the entry installed?

crontab -l

Check spelling, field positions, the intended user, and whether the command has been saved.

3. What do the logs say?

sudo journalctl -u cron --since "1 hour ago"

On some Ubuntu installations, cron activity may also appear in /var/log/syslog. Log availability depends on system configuration.

4. Does the command work manually?

bash -n /absolute/path/to/script.sh
bash /absolute/path/to/script.sh

Check the script's syntax, dependencies, permissions, paths, and configuration.

5. Check output and permissions

Inspect the job log, verify the log directory is writable, and check that the scheduled user can read the script and access the required files.

Common errors and likely causes

Symptom What to investigate
command not found Cron's PATH, absolute executable paths
No such file or directory Incorrect script path, missing interpreter, wrong working directory
Permission denied Execute/read permissions, parent-directory permissions, service-account access
Works manually but not in cron Environment variables, current directory, shell assumptions, permissions
Log file stays empty Schedule timing, service state, redirection path, script output
Job runs twice at once Runtime exceeds interval, missing lock or coordination
Script exits nonzero Inspect its error output and return status
Job didn't run while the machine was off Cron normally doesn't replay missed jobs automatically

What about jobs missed while the server is off?

Traditional cron generally does not replay every missed execution after a machine has been powered off. If a task must catch up after downtime, investigate anacron for appropriate periodic jobs or a systemd timer with suitable persistence settings.

For tasks that must execute once per business date, avoid assuming that a simple cron schedule guarantees exactly-once processing. Use application-level tracking or idempotent processing.
