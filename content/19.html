Linux for DevOps — Module 1, Lesson 18

Linux Security Fundamentals and Hardening on Ubuntu

The Beginner's Guide to Securing a Linux Server | Falcon Internet Blog

falconinternet.net

In this lesson, you'll learn how to secure an Ubuntu server using practical, beginner-friendly techniques. We'll build on your knowledge of Linux users, permissions, SSH, systemd, logs, environment variables, and cron.

The goal isn't to make a server impossible to attack. It's to reduce unnecessary access, limit exposure, detect suspicious activity, and recover safely when something goes wrong.

By the end, you will be able to:

  • Apply the principle of least privilege to users and sudo.
  • Review and harden SSH without locking yourself out.
  • Configure Ubuntu's UFW firewall safely.
  • Keep packages updated and understand security updates.
  • Inspect file permissions and authentication logs.
  • Recognize common security mistakes and investigate a realistic incident.

1. What does Linux hardening mean?

Hardening means changing a system's configuration to reduce security risks.

An Ubuntu server might run a Python web application, a Perl validation tool, a database, and SSH for remote administration. Each service or account can create a potential entry point if it is configured carelessly.

Visual overview

Access control

Users, groups, sudo

Secure remote access

SSH keys, validation

Network protection

Firewall, fewer ports

Detection and recovery

Logs, updates, backups

A useful security cycle is:

  1. Prevent unnecessary access.
  2. Detect unusual activity.
  3. Respond to incidents.
  4. Recover using tested backups and a known-good configuration.

Security is an ongoing process, not a single command.

2. Least privilege: give each account only the access it needs

The principle of least privilege means a user, script, or service should receive only the permissions required to perform its job.

For example, a support engineer may need to read application logs and restart one service, but may not need unrestricted root access.

Inspect users and groups

Run these read-only commands:

whoami
id
groups
getent passwd
getent group sudo

To inspect a particular account:

id deploy
getent passwd deploy

Replace deploy with a real account on your server.

  • whoami shows your current username.
  • id shows your UID, primary group, and supplementary groups.
  • getent passwd lists accounts known through the system's configured account databases.
  • getent group sudo shows the members of the sudo group when that group is configured locally.

Understand the privilege boundary

Regular user

Normal files and permitted commands

sudo authorization

Authentication and policy checks

Privileged operation

Only the authorized action should be performed

Use sudo carefully

Check your current permissions:

sudo -l

Run individual administrative commands when needed:

sudo systemctl status nginx
sudo journalctl -u nginx -n 50

Avoid using a root shell for routine work. A typo in a privileged shell can have system-wide consequences.

Important: membership in the sudo group commonly grants broad administrative privileges on Ubuntu. It is not a limited-access support role by itself.

Before changing group membership, inspect the existing policy and understand how it affects the account. Don't remove your own administrative access on a remote server unless you have confirmed another authorized administrator and a working recovery route.

Practical exercise

Inspect your current account:

whoami
id
sudo -l

Write down:

  • Your username and groups.
  • Whether you have administrative privileges.
  • Which tasks actually require elevated access.

No configuration changes are needed for this exercise.

3. File permissions: protect application files and secrets

Linux permissions control who can read, modify, or execute files.

The three permission classes are:

  • Owner — the file's owning user.
  • Group — users in the file's owning group.
  • Others — everyone else.

Permissions are r (read), w (write), and x (execute).

Common permission modes

Mode Meaning Typical use
755 Owner can read/write/execute; others can read/execute Publicly accessible directories and executables where appropriate
644 Owner can read/write; others can read Non-sensitive configuration or documentation
700 Owner only: read/write/execute Private directories
600 Owner only: read/write Private configuration or key files
750 Owner full access; group read/execute Restricted application directories
640 Owner read/write; group read; others no access Restricted group-readable configuration

These modes are examples, not universal defaults. The correct setting depends on the application and which account must access the file.

Inspect permissions before changing them

ls -l /etc/ssh/sshd_config
namei -l /etc/ssh/sshd_config

Example:

-rw-r--r-- 1 root root ... /etc/ssh/sshd_config

This indicates that the owner can read and write the file, while group and others can read it. Your actual output may differ.

Inspect application files too:

ls -ld /opt/myapp
ls -l /opt/myapp

Change permissions deliberately

For a private configuration file owned by your current user:

chmod 600 "$HOME/devops-lab/config/app.env"

For an application directory intended to be accessible only to its owner:

chmod 700 "$HOME/devops-lab/config"

Only use these examples when the current owner is the correct account. A service running as another user may need carefully granted access.

Avoid chmod 777. It grants read, write, and execute permissions to everyone. It can conceal the actual ownership problem while creating a serious security risk.

Never apply recursive permission or ownership changes to /, /etc, /usr, or an entire application tree without first understanding the impact.

4. SSH hardening: secure remote administration

SSH provides encrypted remote access. It is essential for managing many Ubuntu servers, but a poorly configured SSH service can expose administrative access.

Step 1 — Check SSH status

On the server:

sudo systemctl status ssh
sudo ss -lntp

Ubuntu commonly uses TCP port 22, but your server may use a different port or configuration.

Check the effective server configuration if you need to understand what SSH is actually applying:

sudo sshd -T | grep -E '^(port|permitrootlogin|passwordauthentication|pubkeyauthentication)'

sshd -T prints effective settings. Configuration can be influenced by included files and Match rules, so inspect the relevant configuration if the output is unexpected.

Step 2 — Prefer key-based authentication

A common key type for a new user key is Ed25519:

ssh-keygen -t ed25519 -C "devops-laptop"

This creates a private key and a public key in your SSH directory by default.

  • Private key: keep it secret and protected by appropriate permissions; use a passphrase where practical.
  • Public key: can be installed on the destination account.
  • Never send the private key to a server administrator as a substitute for the public key.

If authorized, install the public key:

ssh-copy-id deploy@SERVER_HOST

Replace the username and host with your actual server details. Then test a new SSH session before changing authentication settings.

Step 3 — Harden the server carefully

SSH server configuration is commonly located at:

/etc/ssh/sshd_config
/etc/ssh/sshd_config.d/

Inspect the main file and any included configuration. Settings worth reviewing include:

  • PermitRootLogin
  • PasswordAuthentication
  • PubkeyAuthentication
  • AllowUsers or AllowGroups, where appropriate
  • MaxAuthTries

Disabling root login or password authentication can reduce risk, but only after verifying that the approved administrative account can log in using a working alternative. Some environments deliberately use a managed identity or other authentication mechanism.

The safe SSH change procedure

1. Keep a working session open

Do not close your only administrative connection.

2. Back up the configuration

Make a protected backup before editing.

3. Validate the configuration

Run the syntax check before reloading SSH.

4. Reload and test a second session

Confirm new access works before closing the original session.

5. Keep a recovery route

Use an approved cloud console, hypervisor console, or out-of-band access method.

For a configuration change, the following illustrates the validation procedure. Run it only when you have the required permissions and a planned change:

sudo cp -a /etc/ssh/sshd_config \
  /etc/ssh/sshd_config.backup

sudo sshd -t

If you have edited the configuration, run sudo sshd -t again. No output usually means the syntax check passed. If it reports an error, correct the issue before reloading.

Then, after confirming the intended settings and recovery plan:

sudo systemctl reload ssh

Open a second terminal and test a fresh login. If access fails, keep the original session open and use the recovery plan.

Do not blindly copy a hardening configuration from the internet; the right settings depend on your Ubuntu release, authentication method, and environment.

5. UFW firewall basics on Ubuntu

A firewall controls which network traffic is permitted. Ubuntu's Uncomplicated Firewall, or UFW, provides a convenient interface for common host firewall rules.

Understand the traffic flow

Incoming network traffic

UFW firewall rules

Allow or deny according to policy

Allowed

Blocked

Step 1 — Inspect the current firewall

sudo ufw status verbose

If UFW is not installed, use the normal Ubuntu package-management process to install it. Do not assume that an inactive UFW means no firewall exists; cloud firewalls, network ACLs, other host-firewall tools, and upstream devices may also control traffic.

Step 2 — Understand the rules

For a web server that should accept public HTTP and HTTPS traffic, the common rules are:

sudo ufw allow 80/tcp
sudo ufw allow 443/tcp

For SSH, port 22 is only an example. First confirm the actual SSH port and how you connect. If it is port 22, an example rule is:

sudo ufw allow 22/tcp

If SSH uses another port, permit the actual port instead. If access should be restricted to an approved source IP or VPN, use a narrower rule appropriate to your environment.

Step 3 — Be careful when enabling UFW remotely

Enabling a firewall before allowing your current management connection can lock you out.

Before enabling it on a remote server:

  1. Confirm the active SSH port.
  2. Review the existing firewall and network policy.
  3. Add the required SSH allow rule.
  4. Confirm any necessary application ports.
  5. Ensure you have an approved recovery console.
  6. Only then consider enabling UFW and verify connectivity.

On a disposable local lab or a server where you have confirmed the safe setup, enabling may be done with:

sudo ufw enable
sudo ufw status numbered

Don't run this blindly on a production or remotely managed server.

Step 4 — Inspect and remove rules carefully

sudo ufw status numbered

If you identify a rule that should be removed, verify its number immediately before using:

sudo ufw delete RULE_NUMBER

Replace RULE_NUMBER with the displayed number. Deleting a rule can disrupt SSH or application access; re-check the list after every change.

Which ports should be exposed?

Port Typical purpose General guidance
22/tcp SSH Restrict to approved management sources where possible
80/tcp HTTP Allow if the service needs public HTTP
443/tcp HTTPS Allow if the service needs public HTTPS
3306/tcp MySQL Usually keep private; avoid unrestricted public access
5432/tcp PostgreSQL Usually keep private; allow only approved application sources
8080/tcp Common alternate web port Expose only if required by the intended design

A port being open does not guarantee that a service is listening, and a listening service is not necessarily reachable from the internet. Check both host and network controls.

6. Security updates and package hygiene

Outdated software can contain known vulnerabilities. Regularly review updates and apply them according to your organization's maintenance and testing policy.

Step 1 — Refresh package information

sudo apt update

This refreshes package indexes. It does not install all available updates.

Step 2 — Review available upgrades

apt list --upgradable

You can inspect a specific package's candidate version with:

apt-cache policy openssh-server

Step 3 — Apply updates responsibly

On a suitable lab machine:

sudo apt upgrade

On production servers, follow the maintenance policy, change approval process, and service-restart requirements. Review any proposed removals or major changes before proceeding.

For security-related updates, Ubuntu provides the unattended-upgrades mechanism on many installations. Inspect its status and configuration rather than assuming automatic updates are enabled:

systemctl status unattended-upgrades

You can check whether the package is installed with:

dpkg -s unattended-upgrades

The service status alone doesn't prove that all security updates are being installed. Configuration, repository settings, package holds, and maintenance policies affect behavior.

Useful security maintenance commands

cat /etc/os-release
sudo apt update
apt list --upgradable
sudo journalctl --since "24 hours ago" -p err

For production, also maintain:

  • Tested backups and a recovery plan.
  • An inventory of installed packages and exposed services.
  • A process for applying urgent security fixes.
  • Monitoring for failed updates and service restarts.
  • A supported Ubuntu release with a suitable security-maintenance plan.

Remember: updates reduce known vulnerabilities, but they do not replace access controls, network restrictions, or monitoring.

7. Authentication logs and security monitoring

Logs can help you investigate failed logins, service failures, and suspicious activity.

On Ubuntu systems using systemd, the journal is often a useful starting point.

Inspect SSH service logs

Depending on the Ubuntu release and SSH unit configuration, use:

sudo journalctl -u ssh --since "1 hour ago"

For recent entries:

sudo journalctl -u ssh -n 100 --no-pager

Follow new entries while troubleshooting:

sudo journalctl -u ssh -f

Press Ctrl+C to stop following logs.

Inspect authentication records

On systems using the traditional authentication log:

sudo tail -n 100 /var/log/auth.log

To look for common SSH authentication messages:

sudo grep -iE 'failed password|accepted publickey|invalid user' \
  /var/log/auth.log | tail -n 50

The file may not exist on every Ubuntu installation, and logging formats can vary. If it is absent, inspect the system journal and the relevant logging configuration rather than assuming logging is broken.

What do the messages mean?

Log message Possible interpretation
Failed password An authentication attempt failed
Accepted publickey A public-key login succeeded
Invalid user A login was attempted for an unknown account
Connection closed A connection ended; context determines whether it matters
Repeated attempts from one source Could indicate automated scanning or a brute-force attempt

A failed login is not proof of a successful compromise. Internet-facing servers routinely receive automated connection attempts. Look at timestamps, source addresses, account names, successful logins, and surrounding activity before drawing conclusions.

Check who is currently logged in

who
w
last

These commands provide session or login-history information based on available system records. They are useful signals, but not a complete security audit.

Optional: audit with auditd

For systems that need more detailed auditing, Linux Audit can record selected system events.

Check whether the audit service is installed and running:

systemctl status auditd

If your environment requires it, install and configure auditd through the approved package and security process. Audit rules should be chosen for a specific monitoring need; excessive rules can create large volumes of data. Use the applicable tools and retention policy to review audit events.

Security monitoring is most useful when logs are retained, access-controlled, and reviewed or alerted on—not merely collected.

8. Common Linux security mistakes

Mistake 1: Using chmod 777 to fix access errors

Better: inspect ownership, group membership, parent-directory permissions, and the service account. Grant only the necessary access.

Mistake 2: Disabling SSH password login before testing key access

Better: test a fresh key-based session first and keep a working session and recovery route.

Mistake 3: Enabling a firewall without allowing SSH

Better: inspect the active port and rules, confirm the management path, and prepare recovery access before enabling.

Mistake 4: Leaving secrets in scripts or logs

Better: use an approved secret-delivery method, restrict access, avoid tracing sensitive commands, and rotate exposed credentials.

Mistake 5: Updating production packages without a plan

Better: review changes, follow maintenance policy, prepare recovery, and verify service health afterward.

9. Realistic DevOps case study: securing a journal validation server

Imagine your Ubuntu server runs a Perl-based journal delivery validator. The server has SSH access, a scheduled health check, and an internal web application.

A routine review reveals three concerns:

  • A service configuration directory is readable by more accounts than necessary.
  • SSH authentication logs contain repeated failed login attempts.
  • The firewall and exposed application ports have not been reviewed recently.

Your task is to reduce risk without disrupting journal processing.

Step 1 — Collect evidence before making changes

Run read-only checks:

whoami
id
sudo -l
sudo ss -lntup
sudo ufw status verbose
sudo journalctl -u ssh --since "24 hours ago"

If the traditional authentication log is present:

sudo tail -n 100 /var/log/auth.log

Inspect relevant application directories:

ls -ld /opt/myapp
ls -l /opt/myapp

Record which services are listening, which users own application files, and whether SSH authentication attempts succeeded or failed.

Step 2 — Rank the risks

Finding Investigation Possible remediation
Broad file permissions Identify who needs access Correct ownership and narrowly scoped permissions
Repeated SSH failures Review sources, timestamps, and successful logins Restrict access, review authentication policy, and add appropriate monitoring
Unexpected listening port Identify the process and business purpose Remove or restrict exposure only after confirming dependencies
Outdated packages Review candidate versions and maintenance policy Apply approved updates and verify service health

Don't automatically block an IP just because it has failed logins, and don't close a port without checking whether a legitimate application or monitoring system depends on it.

Step 3 — Implement changes safely

For SSH, verify the intended administrative account and authentication method, validate configuration, and test a second connection before closing the original.

For UFW, identify the required management and application ports before changing the rules. If this is a remote server, confirm console recovery access.

For file permissions, correct only the affected paths and confirm the validation service can still read its required files.

For updates, follow the server's maintenance procedure and check whether a restart is required.

Step 4 — Verify the result

After each approved change, verify the relevant component.

sudo systemctl status ssh
sudo ufw status verbose
sudo ss -lntup
sudo journalctl -u ssh --since "30 minutes ago"

Then run the existing health check from Lesson 15, if its service argument matches the service you intend to test:

bash "$HOME/devops-lab/health_check.sh" cron 80

A successful health check is one signal, not proof that the entire server is secure. Confirm application-specific functionality and the expected scheduled processing as well.

Step 5 — Document the outcome

A useful incident or change report should include:

  • Initial finding and supporting evidence.
  • Affected service or files.
  • Change made and why it was necessary.
  • Validation performed before and after.
  • Remaining risks and rollback procedure.

The key DevOps habit is measure, change deliberately, verify, and document—not blindly running a list of hardening commands.

Optional investigation challenge

Imagine a process is listening on TCP port 8080, but the application owner says it should be internal only.

Use these commands to investigate without changing anything:

Answer these questions in your notes:

  2. Is it bound to 127.0.0.1, a particular interface address, or 0.0.0.0?
